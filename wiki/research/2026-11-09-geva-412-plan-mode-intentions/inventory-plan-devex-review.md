## Claimed value, one sentence

The skill exists to make a plan's developer-facing product easy to adopt: it pins down who the developer is, how fast they reach a first useful result against a benchmarked target, where the journey from install to upgrade breaks, and whether errors let an agent or a human recover, then turns each gap into an explicit, user-approved change to the plan (S185-191, S458-460, S199-207, T6-12).

## Steps vs intention

1. **Self-rated scores decide "clean".** The log status is "clean" when the score is 8+ and nothing is unresolved (R829). The same model fills the scorecard and the principle coverage (R621-647), and the method has it apply its own changes and then re-rate (S797). A plan can move from 4 to 8 by adding paragraphs, with nothing measured. The text warns that a score is not measured success (S798, R34-35), but no outside check exists. The formatting rule to rate before and after each pass (R1023) rewards visible score gains.

2. **The TTHW number is usually an estimate, and the outputs can drop that label.** Step 0C asks for evidence types and says to keep estimates labeled until measured (S609-614, S623-625). But the scorecard TTHW row and Competitive Rank have no evidence-type field (R632-633), the log stores `tthw_current` and `tthw_target` as plain strings (R826), and "TTHW > 10 min: flag as blocking" (R652) fires on a guess. DX-2 is met only by a measured time after launch, which the skill leaves to /devex-review (R993-996).

3. **Roleplay with simulated timestamps.** Step 0G asks for a confusion log with timestamps that "simulate real time passing" (S760-761, S770-774) and also demands it be "Not hypothetical" (S777). The 0B narrative is model-written, and the skill admits that user confirmation is not observation (S280). Both can be produced fluently with no real trace. The guard is the demand to cite README headings, errors and file paths (S778), which an evaluator can check.

4. **The DX Implementation Checklist can be ticked with no substance, and it conflicts with POLISH.** Its 17 boxes are generic (R656-676); "Free tier available, no credit card", "TypeScript types" and "Search works in documentation" appear whatever the product is. In POLISH a checklist is "a lens, not a requirement" (R31-32). Nothing says who ticks it or when, and nothing returns to it at BUILD.

5. **The error matrix samples four paths but the checklist claims all of them.** Pass 3 traces 3 specific paths plus 1 unexpected path (R170-172), while the checklist says every error message meets the contract (R663). In a plan review, adding error-text specs to the plan turns fails into passes (R165, H73-74), while the BUILD can still ship the old errors. The real test is the shipped error output (DX-5, BUILD).

6. **The anti-skip rule can be met with one line.** All 8 passes must be evaluated (R5), but "No issues found" is allowed (R5, R563). A run can name every pass and do no tracing. Proof of work is cited evidence per pass and a Hall of Fame section read per pass (R107, R136, R162, R196, R212, R230, R248, R264).

7. **The Mode Quick Reference contradicts the body.** It says TRIAGE skips the outside voice (R1014), but the outside voice is default-on and only the config switch disables it (R304-308, R335-340). It says TRIAGE does "Target only" for competition and that POLISH and TRIAGE only "Verify exists" for the magical moment (R1009-1010), but the Priority hierarchy says never shorten the benchmark or the magical moment (S268-270), and 0D always asks a design question (S666-680).

8. **The runner profile cannot meet the main intentions as written.** In unattended or `--light` autoplan runs (lib/autoplan-run.ts:179) and every lean run (lib/autoplan-lean.ts:123), the DX reviewer gets the checklist (C1-34) appended to a short brief (bin/gstack-autoplan-snapshot.ts:54-61, or lib/autoplan-prompts.ts:133 in a lean run). The checklist demands "Step 0 complete" with persona, narrative, benchmark and magical moment, and "One decision cycle per unresolved finding" (C9-15). That reviewer is blind, cannot ask the user, and must return prose plus a `gstack-findings` fence (lib/autoplan-prompts.ts:118-128). So persona confirmation, the approved target and approved decisions (DX-1, DX-2, DX-7) cannot happen there, and nothing in the result format checks the 14 required outputs listed in C17-34. The checklist block also tells the reviewer that the methodology file holds the full sections (lib/autoplan-prompts.ts:197), but the reviewer is never given that file's path; the methodology bundle is for the parent driver (bin/gstack-autoplan-snapshot.ts:589).

9. **Full (non-light) autoplan DX reviewers get less DX method, not more.** In full mode, `sectionLoadFor` returns no checklist and only names `review-sections` as loaded (lib/autoplan-prompts.ts:172-178), and `writePrompts` injects only the checklist (lib/autoplan-prompts.ts:197, 203). The native DX reviewer then sees only the 5 criteria in bin/gstack-autoplan-snapshot.ts:54-61: getting started, ergonomics, errors, docs and escape hatches. Upgrade, environment, community and measurement (Passes 5-8) are absent. Whether the parent driver runs the full methodology itself is set by autoplan/SKILL.md and its DRIVER.md, which I did not read.

10. **Two different applicability gates.** Interactive runs exit when the plan has no developer-facing surface (S374-386). The runner turns the DX phase on when the Implementation plan has 2 or more matches from a broad term list that includes "implement", "command", "agent", "action", "debug" and "import" (bin/gstack-autoplan-snapshot.ts:12-20). Almost any plan triggers a DX review in autoplan, including plans the interactive gate would turn away.

11. **Measurement is optional.** Pass 8 says a target tier does not itself approve telemetry or a release gate, and to ask only when proposing one (R275-277). A plan can pass Pass 8 with no instrumentation. That leaves DX-2 and DX-14 unverifiable after launch unless someone runs /devex-review.

12. **The DX review never shows on the readiness dashboard.** Its rows are Eng, CEO, Design, Adversarial and Outside Voice (R843-849, R904-910). The DX row appears only in the plan's GSTACK REVIEW REPORT table (R768), so a DX review cannot clear or block anything on the dashboard.

13. **Volume.** Step 0 alone needs six blocking questions in a fixed order (product type S391, persona S514, empathy S603, target S647, magical moment S680, mode S715 unless already chosen), then one question per friction point, per pass decision, per TODO (R598-599) and per outside finding, plus 11 plan sections before the report. Length and question count are easy to produce and say nothing by themselves about developer outcomes.

## Notes

- **No generator drift.** The dry-run reported every plan-devex-review file FRESH. The differences between .tmpl and generated text are intended by the generator:
  - Frontmatter: T4 `interactive: true`, T13-19 `voice-triggers`, T20 `benefits-from: [office-hours]` and the long description T6-12 are absent from S1-18; S5 keeps only a one-line description. The four pillars (personas, benchmarks, magical moments, friction) are stated only in the tmpl description, not in any runtime file.
  - RT420 `{{GBRAIN_SAVE_RESULTS}}` renders to nothing (blank lines R940-942).
  - CT and C differ only by the AUTO-GENERATED header (C1-2).
- **Stale comment.** lib/dx-error-contract.ts:3-4 says the full contract renders into Pass 3 through `{{DX_ERROR_CONTRACT}}`, but RT126 uses `{{DX_ERROR_COMPACT}}` and points to the Hall of Fame for the full text (R167-168). H44-82 holds the full contract as static text; on my read it matches `DX_ERROR_CONTRACT` (lib/dx-error-contract.ts:21-59) word for word, but I found no test that keeps H in sync with that constant. bin/gstack-autoplan-snapshot.ts:34-36 says a test keeps its compact copy in sync.
- **Name mismatch.** 0B says the narrative becomes the required "Developer Perspective" output (S604), but Required Outputs call it "Developer Empathy Narrative" (R576).
- **Pass 1's fixed bar vs the chosen target.** Pass 1 asks whether hello world takes under 5 minutes (R101) even when 0C approved "Current trajectory" or a custom target (S642-645).
- **Unattended gap in the office-hours offer.** S521 skips the offer only for spawned or headless sessions. An unattended session still raises it, and the offer then auto-decides.
- **Dashboard omission.** The readiness dashboard has no DX row (R843-849), although the report table has one (R768) and review-dashboard.ts lists plan-devex-review log fields (grep, lines 139 and 169).
- **Two log shapes.** Interactive runs log mode, persona, competitive tier and `dimension_scores` (R826). The /autoplan copy (autoplan/SKILL.md:709, grep only) omits mode, persona, competitive_tier and dimension_scores and adds `"via":"autoplan"`. An eval that reads trends or per-dimension scores from autoplan rows will find them missing.
- **Which score is "8+".** R829 does not say whether the initial or overall score sets "clean"; the row carries both.
- **Persona exclusion.** The AI coding agent persona is offered for every type except Documentation (S500), while the error contract still applies to Documentation in reduced form (H70).
- **Hall of Fame figures.** H13, H157-158, H168, H173-176 and H180-181 quote adoption and productivity numbers with names but no links. The skill's own rule says illustrations are not measurements (S619); an eval should not reward copying them into a plan as evidence.
- **Eval design pointers.** The strongest AFTER evidence is a measured TTHW for the approved clock (DX-2), shipped error output scored against the contract (DX-5) and a /devex-review row (DX-14). The strongest PLAN evidence is decision records that match plan diffs (DX-7) and cited file:line evidence per pass (DX-4, DX-6). Scores, checklists and principle coverage are self-reported and weak.
