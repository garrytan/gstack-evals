## Claimed value, one sentence

Before code is written, the skill makes a UI plan say exactly what users will see and do (hierarchy, every state, the journey, responsive and accessible behavior, and a specific non-generic look checked against DESIGN.md and an approved mockup), with the user deciding each change, so the shipped UI is intentional instead of left to the implementer (SKILL.md:23-26, 221-224, 236-237, 239-259; RS:5).

## Steps vs intention

1. **The model grades itself.** Pass scores, re-rates after fixes, the overall score (lowest pass), the "Plan is design-complete" line and the log's `clean` status all come from the model's own 0-10 ratings (SKILL.md:393-396, 785; RS:82-84, 358-361, 387, 517). A run can lift every pass to 8+ by re-rating after its own wording edits, and the log will say clean. Nothing outside the model checks a score.
2. **The procedure can be followed with no build ever checked.** Most of DES-3 to DES-6 are properties of shipped pixels (16px body, 4.5:1 contrast, themed focus rings, 44px targets; RS:196-207, 248). The skill admits it can only assess what the plan says when no render exists (RS:130). The one step that would check the build, /design-review, appears only in the completion line (RS:387) and is not an option in the next-step menu (RS:686-690). A perfect run can precede a shipped UI that breaks every rule.
3. **Tables can be ticked with no substance.** The state table, storyboard, ASCII hierarchy and Pass 7 decision table (RS:90, 101-106, 113-119, 257-263) can be filled with generic cells ("spinner", "error toast", "user feels confident"). Pass 2 asks for what the user sees (RS:107), but the format does not test specificity. The state table grows with feature count, so it rewards volume.
4. **One question per issue rewards question count.** "Never batch" (RS:97, 280; SKILL.md:844-845) and gstack's own floor test, which passes when at least one AskUserQuestion fires (test/skill-e2e-plan-design-finding-floor.test.ts:1-7), measure the procedure, not the plan. Many shallow questions pass. A user who answers "good enough, move on" (SKILL.md:786) ends the loop with gaps that stay below 10, which is allowed.
5. **"User decides every change" turns off without a human.** In a `spawned` or `unattended` session the shared preamble auto-chooses the recommended option at every decision point (scripts/resolvers/preamble/generate-ask-user-format.ts:15), and the exit gate accepts "preamble-authorized per-issue auto-decisions" (SKILL.md:846; RS:32). Question Tuning `AUTO_DECIDE` does the same per question id (SKILL.md:107). Under /autoplan the design phase auto-fixes structural issues and auto-decides each issue (autoplan/sections/design-phase.md:6-9, 117), which contradicts "Even obvious fixes need approval" (SKILL.md:223). An eval harness with no live user cannot observe DES-8 as written.
6. **Anti-skip vs early exit vs focus areas.** RS:5 says never skip a pass "regardless of plan type (strategy, spec, code, infra)". SKILL.md:295 exits early on a plan with no UI. Step 0D offers to focus on specific areas instead of all 7 (SKILL.md:406), while the priority hierarchy forbids shortening Passes 1-7 (SKILL.md:263-265), and a rerun gives 8+ sections only "a quick pass" (SKILL.md:797). The model has to pick which rule wins.
7. **The mockup quality check is weaker than its words.** The text says check "each saved path" (SKILL.md:465) but the command checks only the first path (SKILL.md:470). `$D check` returns `pass: true` with `status: "skipped"` when the vision call fails (design/src/check.ts:11-12, 69, 74), so a model reading `pass` treats an unchecked image as passed. The check covers readability, completeness and coherence (check.ts:51-54), not the slop list; slop is caught only if the model also does Pass 4's mockup read (RS:235).
8. **The approved mockup lives where the builder may not see it.** Mockups must stay under the private state root, never `docs/designs/` (SKILL.md:341-344), and the Approved Mockups table records an absolute local path (RS:402). DES-7 wants it to be the reference for what gets built, but a teammate, CI or a lane on another machine cannot open it.
9. **Fallback contradiction when the designer is missing.** DESIGN SETUP says fall back to "the existing HTML wireframe approach (`DESIGN_SKETCH`)" (SKILL.md:323-325). Step 0.5 says do not substitute hand-built HTML/CSS wireframes and continue text-only (SKILL.md:609). The first comes from a shared resolver, the second is skill-specific.
10. **The runner profile drops almost all of the method.** See the next section. The checklist names passes and outputs only (CL:8-28), and its step 4, "one decision cycle per unresolved finding" (CL:15), cannot happen unattended. Its required outputs (Completion Summary, Approved Mockups, Review log row; CL:24-27) belong to the interactive flow; the runner reviewer writes a findings file, not the plan.
11. **"Initial score" is ambiguous.** The log's `initial_score` is "initial overall design score before fixes" (RS:518), while the summary keeps Step 0's impression in its own row and computes the overall from pass scores (RS:358-360). Two different numbers can be logged as initial.
12. **The retrospective check looks in the wrong place.** It says check git log for prior design review cycles (SKILL.md:291-292), but reviews are logged to the gstack state root (RS:508-509), not git. The audit map does say check reviews.jsonl (SKILL.md:289).
13. **The design review never gates shipping.** The dashboard marks Design Review "Required: no" and the verdict depends only on Eng Review (RS:574-582, 601). An `issues_open` design review has no downstream effect, so AFTER evidence for DES-2 to DES-6 depends on someone acting on the plan.
