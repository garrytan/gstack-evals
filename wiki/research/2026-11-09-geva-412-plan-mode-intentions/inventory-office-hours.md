## Steps vs intention

1. **The founder signal count is self-rated, and it sets the pitch.** The model decides which of eight signals it saw (SKILL.md:568-578) and logs them (:605-606). The count picks the YC pitch tier, including the line that GStack thinks the user is among the top people (design-and-handoff:410-416). Nothing outside the model checks a signal, so a run can follow every step and inflate the count. The anti-slop rule (design-and-handoff:392-396) governs wording, not accuracy.
2. **The spec review checks document quality, not demand truth.** The reviewer scores Completeness, Consistency, Clarity, Scope and Feasibility (lib/office-hours-review.ts:296-302). It cannot see the conversation (design-and-handoff:206), and it is told unknown customer facts may stay as open questions (lib/office-hours-review.ts:277). A doc with vague or invented Demand Evidence, or "What I noticed" quotes that never happened, can PASS. The quality_score is a number a same-harness subagent assigns (lib/office-hours-review.ts:29; design-and-handoff:117 notes the same-harness limit for the second opinion).
3. **Forcing questions can be asked without forcing anything.** Smart-skip lets the model judge a question already answered (2a:154). The escape hatch ends the diagnostic after two more questions, or at once on a second push (2a:158-162). The template still asks for Demand Evidence, Target User and Wedge (design-and-handoff:66-73), so those sections can be filled from soft answers. The steps measure that questions were asked, not that answers got specific; only the transcript shows a push.
4. **The builder escape hatch skips the premise challenge.** On impatience or "just do it", builder mode fast-tracks to Phase 4 (2b:43) and skips Phase 3. Important Rules keep Phase 3 even for full plans (SKILL.md:679), and the second sentence of 2b:43 keeps it for full plans too. OH-6 can fail in builder mode while the builder steps are followed to the letter.
5. **The builder Assignment has no home.** Important Rules make a concrete real-world action mandatory every session (SKILL.md:678). The profile logs the assignment from "The Assignment" section in both modes (SKILL.md:608), and welcome-back asks about it (design-and-handoff:448-449). But the builder template has no The Assignment section, only Next Steps build tasks (design-and-handoff:160-161); builder posture says "not who to interview" (2b:25); and the reviewer contract protects only the startup Assignment (lib/office-hours-review.ts:277). "Met" for OH-9 in builder mode is undefined.
6. **Phase 4 forces implementation approaches even when the diagnosis says "not yet".** The startup principles say interest is not demand and watching beats demos (2a:9, :13). A pre-product founder with no evidence still gets 2-3 implementation approaches with Effort and Risk (SKILL.md:522-544), and the closing example says the design can be built this weekend with Claude Code (design-and-handoff:398). The format rewards producing approaches, and the role rules (one minimal viable, one ideal) can be met with a filler option.
7. **Premise agreement rewards compliance.** The model writes the premises and the user answers agree or disagree (SKILL.md:497-505). All-agree satisfies the step; only disagreement loops. Premises written to be agreeable pass.
8. **The second opinion is scored by a code-review classifier.** The prompts ask for a steelman, a key quote, a wrong premise and a 48-hour prototype (second-opinion:60-62). The run block also asks for a severity per finding and a VERDICT line (:66) and classifies with gate `review` (:97). That gate needs a `Recommendation: ... because ...` line, and numbered items without severity beside a VERDICT make it unverified (lib/outside-review-result.ts:266-282). A good cold read can be scored unavailable or unverified, which sends the run to the Claude subagent fallback (second-opinion:113-121). The boundary text also says to review only repository code (:57), which does not fit a brainstorm summary. The founder signal for defending a premise against Codex (SKILL.md:576) depends on this path.
9. **The success check checks a file, not approval.** "DESIGN_DOC: ok" only tests that a non-empty file exists at the exact path (SKILL.md:635), and OUTCOME success follows it (:643-645). Status: APPROVED (design-and-handoff:306) is never checked.
