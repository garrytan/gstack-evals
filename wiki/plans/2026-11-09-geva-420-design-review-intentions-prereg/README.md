# Preregistration: does gstack's design plan review make shipped screens handle their states, layout and accessibility?

## Approval

Gate 1 of the plan-mode intentions program was approved on 2026-11-09 by the project owner through the Captain, after one lean gstack /autoplan review of the program plan (run autoplan-v2-20261109020744, gate revision 1). The owner took every recommendation. For this eval that means: its own headroom stage before any comparison money (A1), the product-value eval's leak guards (B1), one failure-scoring table (C1), a smoke of every gstack arm on every model with one repair or a drop (D1), autoplan run inside the same session as the other arms (E1), separate verdicts for the skill and for autoplan (F1), a power script and a stated MDD (G1), one offline code snapshot for every arm (H1), sandboxed build runs (I1), a recovery rule for paid sessions (J1), the outcome-per-skill program's family U folded in with its line raised to a $4,000 all-in guideline because GPT-6 Astra judges (M1), Capy's default lean autoplan as the autoplan arm (O1), real public changes from after the models' training cutoff (P1) and no rebuilt candidate skill (R1). This post's own review, under R65's path for a paid-eval preregistration, was one lean /autoplan run (run1-20261109041448) with one cross-family reviewer. The Captain answered its gate (gate_rev 1, rec_hash d72218c42f53) on 2026-11-09, taking every recommendation and accepting the deviations in section 18. This post approves no item's spend: no paid call runs until it merges and the Captain records each item's cap.

## ELI5

gstack has a skill, plan-design-review, that reviews a plan the way a senior product designer would, before anyone writes code. It is meant to make the plan say exactly what people will see and do: what comes first on each screen and what the next step is, what the screen shows while it loads, when it is empty and when something fails, how it works on a phone and with a screen reader, and how it fits the project's existing design. Nobody has tested whether it does that. Our only earlier test of it planted flaws in plans and couldn't read a result. This test uses what really happened. We take real changes that open-source teams merged in public web, mobile and desktop apps after the models' training cutoff, where the change added or reworked a screen. For each change we already know the next two months: the UI problems users reported and the UI fixes the team made, such as a list that showed nothing while loading, a dialog that broke on small phones, a button a screen reader couldn't name, or a new card that ignored the theme. Each reviewer gets the team's plan and the code as it stood before the change, and writes up to eight short changes it would make to the plan. A change scores when it names the screen and the exact problem that later showed up. A long list can't win, because only eight short changes count and stock design advice must score near zero. We compare four setups on Opus 5.5, GPT-6.1 Sol and particle-1: no gstack, a one-line "senior product designer" prompt, the skill, and autoplan's default run, which carries only a short design checklist. Judges come from a different model family than the model judged, and they are checked against known answers before any number counts. On up to 16 changes whose screens run in a browser, a plain agent then builds each one from each reviewed plan, and we render the result on three screen sizes, count accessibility violations, force the empty, error and loading states, check whether the real later problem comes back, and have an agent user try to finish set tasks in it.

## Before → after

Before: plan-design-review has eight main intentions and none is fully scored. Panel v3's design stratum (#191) planted design flaws in plans and read NO READ, and the outcome-per-skill program's family U was approved but never preregistered. Its agent-user primary could not reach a usable MDD, so its comparison was set to wait for a cheaper agent user.

It reports, per model with paired intervals, whether plan-design-review and autoplan's default lean run each name more of the screens and conditions where real UI problems later landed than the same model with no gstack, and than a one-line product-designer prompt. A headroom check runs first, a judge check gates every verdict, and a build stage on up to 16 units shows what ships, descriptively. It names the six main intentions it scores and the two it leaves untested.

## Why it matters

plan-design-review loads in every interactive design review and, as a short checklist, in autoplan's default run whenever a plan touches UI, so most UI plans that go through gstack meet some form of it. If it works, builders should keep it and autoplan should carry more of it. If plain Opus already plans these states and layouts, the procedure costs time and tokens for nothing. Today nobody knows, and the crew's rule forbids a cut while a main intention is untested.

## Big decisions

1. **Primary construct and score.** Options: (a) aftermath anticipation: the share of a change's real UI aftermath (user reports and follow-up UI fixes in five classes: states, hierarchy and navigation, responsive layout, accessibility, design-system fit) that the review's capped list of plan changes names, screen and condition both; (b) a judged quality score of the reviewed plan; (c) building from each reviewed plan and checking what ships. Pick (a) as the primary, (b) as a length-controlled pairwise secondary and (c) as a descriptive stage 3 on up to 16 units, as the program plan set. Why: (a) is grounded in what happened after the plan and dated after it, so no reviewer can copy it and no judge's taste sets it; (c) answers the "shipped UI" half of the claim but costs several times a review per cell. What would flip it: stage 1 reading FLOOR, which makes (c) the primary of the next attempt.
2. **The scored artifact.** Every arm writes the same neutral block: at most eight changes to the plan, 40 words each. The template names no screen, state, viewport or user, so the none arm gets no design lens from it. The lens arm then measures what one line of framing adds.
3. **The gstack pin.** Both gstack arms run gstack b6155921a564ba9ec2470fd2cb3894c05e2c2d13 (VERSION 1.98.0.0), the commit the intentions inventory read, so the intentions scored are the intentions shipped.
4. **The autoplan arm.** Capy's default lean run (O1): one reviewer whose prompt merges the CEO and Eng lenses and adds a 28-line design checklist and a two-sentence designer role when gstack detects UI scope. It runs inside the same Claude Code session as the other arms, its reviewer a same-model subagent, and the harness answers its gate rec (E1). This is the form people run; it is not the full design phase.
5. **Forcing the procedure, and the one repair.** The skill arm is named with one fixed sentence (run the whole procedure unattended, taking the recommended option at every decision), a detector frozen per arm reads exposure, and a smoke of 6 sessions per gstack arm per model runs before any comparison money. The repair D1 allows once is the harness's Stop hook (section 10), because the forced sentence is already in use and plan-design-review has no opt-in gate.
6. **Models and size.** Opus 5.5, GPT-6.1 Sol and particle-1 each run all four arms (R54): 16 calibration units for stage 1, and 64 comparison units for stage 2 with Opus at 2 passes and the other two at 1. At 64 units power.txt puts the Opus MDD at Holm's first step at 0.12 at the planning point (Opus none at 0.20, 1 or 2 key items a unit, units clustered by repository), the smallest effect worth acting on, and at 0.09 with 2 to 4 items a unit. The stricter admission read, power of at least 0.80 at a lift of 0.12, sits just under the bar at the planning point (0.785) and well over it with 2 to 4 items (0.991), so it runs again on the measured design before stage 2, and a set that fails it grows within the line or goes to the Captain. What would flip it: key yield. The shared frame's full reads found a key item in 1 of 2 UI changes and 1 of 12 developer-facing ones, so authoring starts with a free screen and a paid pilot whose measured yield re-sizes the set before more money goes in, never below 48 comparison units.
7. **No cut can come from this eval.** DES-7 (approved mockups settle the look) needs gstack's compiled designer binary and an image key, which no arm's container holds, and no planned eval scores it; DES-8 (the user decides each change) waits for wave 2's owner-control eval. Under the program's verdict rule a CUT-CANDIDATE needs every main intention scored somewhere, so a null here reads "no measurable difference" and R48 FIX-METHOD on task fit. G1 allows exactly this: the post says so instead of sizing units to a cut bound. The +0.05 bound still prints, as a lead for the trim track only.
8. **Stage 3.** Up to 16 permissive comparison units whose screens render in a browser, with six builds each (the plan alone, the plan with each of the four arms' blocks, and a generic-look control), all by Opus 5.5 with no gstack in a throwaway sandbox (I1). It folds in family U's agent user on frozen tasks and reads DES-4 (a specific, non-generic look) only as a blind pairwise of screenshots against the generic-look control. It decides nothing except a flag on KEEP.
9. **Units.** Real public changes only (P1), from the shared frame and miner the devex eval owns for both evals, taken as written: this eval draws the frame's UI side, which the frame's count found mostly mobile and desktop, with web scarce. The program's transposed fallback isn't built here, because every arm reads the unit's code and a whole codebase can't be re-skinned faithfully; a shortfall goes to the Captain.

## Implementation plan

### 1. The question, the claimed value and construct fit

**Question.** For each model under test, on real UI feature changes merged after Opus 5.5's stated training cutoff in public web, mobile and desktop apps: does a review by plan-design-review, or by autoplan's default lean run, name more of the screens and conditions where the change's real UI problems later landed (missing or broken states, confusing hierarchy or navigation, responsive breakage, accessibility defects, drift from the design system) than the same model with no gstack, and than the same model with a one-line product-designer prompt?

**The public lesson this eval is after (R79), for someone building agents:** whether a written design-review procedure makes a frontier model's plan anticipate the UI problems real users later hit, beyond what the same model writes when simply asked to improve the plan or told to act as a product designer; whether autoplan's default run, which carries only a short design checklist, keeps any of that; and so whether builders should ship a design-review procedure, a one-line role, or nothing.

**Claimed value, in one sentence** (the inventory's, at b6155921): before code is written, the skill makes a UI plan say exactly what users will see and do (hierarchy, every state, the journey, responsive and accessible behavior, and a specific non-generic look checked against DESIGN.md and an approved mockup), with the user deciding each change, so the shipped UI is intentional instead of left to the implementer.

**Intentions scored and untested.** The inventory (wiki/research/2026-11-09-geva-412-plan-mode-intentions/inventory-plan-design-review.md, gstack b6155921a564ba9ec2470fd2cb3894c05e2c2d13) lists eight main intentions. This eval scores six and leaves two untested:

| Main intention (inventory wording, shortened) | How this eval scores it | Status here |
|---|---|---|
| DES-1: the plan itself ends up holding the missing design decisions, written in before implementation | every arm's scored artifact is a list of changes to the plan; a credited change is a design decision the plan lacked that the shipped UI later needed | scored (primary, all classes) |
| DES-2: every screen has a clear first, second and third thing, one obvious next step and wayfinding; the journey is designed across screens | key class H; stage 3's agent-user completion, steps and dead ends | scored (primary H; stage 3 descriptive) |

| DES-4: a specific, intentional look, not generic AI output | stage 3's blind pairwise of rendered screenshots against a stock generic-look control | scored descriptively only; it decides nothing |
| DES-5: responsive behavior per viewport and accessibility specified in the plan | key classes R and A; stage 3's three viewports and axe-core counts | scored (primary R and A; stage 3 descriptive) |
| DES-6: design decisions fit the design system and existing UI | key class Y; stage 3's hard-coded values against tokens | scored (primary Y; stage 3 descriptive) |
| DES-7: generated mockups the user picks settle the visual direction | not scored: it needs gstack's compiled designer binary and an image API key; no arm's container holds a key and the metering proxy admits only the arm's model, so the skill prints DESIGN_NOT_AVAILABLE or fails its first image call and goes on text-only | untested, in every planned eval |

Secondary intentions DES-9 to DES-25 are not scored. A few print as exposure evidence (the Completion Summary of DES-17, the implementation tasks of DES-15) and never enter a score.

**Construct fit.** The claim's core is that the shipped UI is intentional rather than left to the implementer. The primary key records exactly the places where it wasn't: what users reported and what the team had to fix in the reviewed change's own screens within 60 days. Each skill part that carries the claim, at b6155921, and the key items it can reach:

|---|---|---|

### 2. Ground truth: what happened after each UI change merged

Every unit is a real change its maintainers merged that added or reworked something users see. Its key lists what happened to that UI in the 60 days after the merge, from two sources:

- **User reports.** An issue or discussion opened inside the window by someone other than the change's author, not a bot, that describes a problem in the change's own screens or components. It is linked to the change when it cross-references the change's pull request, when a later fix it names (or that closes it) edits UI lines blamed to the change, or when it names a screen or component and the key writer confirms the change introduced or reworked it.
- **UI fixes.** A later merged change that repairs the change's own UI. Candidates come from blame (the eng-review miner's SZZ, widened to stylesheets and templates: a later fix whose edited UI lines blame to the change) and from later changes that touch the change's UI files with a class marker in their diff. The key writer reads each candidate's diff, message and linked issue beside the change's diff and keeps it only when the problem was in the change's own UI.

Each kept item gets one class:

- **S, states.** A missing or broken loading, empty, error, success or partial state, or an edge the screen didn't handle (long text, zero or many results, a first-time user).
- **H, hierarchy and navigation.** Users couldn't find, understand or reach the next step; the screen put the wrong thing first; there was no way back; a primary action's label misled. It needs evidence of confusion: a user report, or a fix whose message or linked issue names it. A copy edit with no stated confusion is not H.
- **R, responsive.** The layout broke at a viewport, orientation, device size, zoom level or safe area.
- **A, accessibility.** Names, roles, labels, focus order or visibility, keyboard reach, contrast, screen-reader announcements or motion.
- **Y, design-system fit.** The change used hard-coded values or one-off components where the project's tokens or components existed, or broke the theme (dark mode, density), and a later change brought it back in line.

Excluded: product reverts and later decisions to change the feature, new features built on top, translations and copy edits with no stated confusion, performance with no visible defect, refactors, test-only and dependency changes, app-wide restyles not specific to the change, and defects outside the UI. A backend error counts only through the screen's handling of it, as S.

**Statements.** Each item is a statement of at most 30 words, written as an observed fact naming the screen, component or flow, the file where it helps, and the condition. Examples written for this post, from no unit: "The new invoices tab showed a blank panel while invoices loaded on slow connections (web/src/billing/InvoicesTab.tsx)"; "On phones narrower than 380 pixels the share dialog's buttons ran off screen (app/components/ShareDialog.vue)"; "The new filter chips had no accessible names, so screen readers announced only 'button' (src/ui/FilterChips.tsx)"; "Later the team replaced the new banner's hard-coded colours with theme tokens because it broke in dark mode (lib/widgets/banner.dart)". Never advice, so the key doesn't read like any arm's style.

**Primary key.** S, H, R, A and Y together, at most 6 items a unit: user reports by people outside the maintainers first, then fixes linked to an issue, then other fixes, then a seeded tie-break (sha256 of the seed, unit and item). Units weigh equally whatever their item count. Each item's class and source print, and A by class and by source are secondaries.

**Mentioned items.** A key item whose screen and condition plan.md or context/ already names as something to handle is flagged mentioned. Mentioned items leave the primary and print as their own stratum, so echoing the plan earns no credit.

**Generic screen.** After the audit, Astra and Opus each label every key item against stock rows 1 and 2 (section 7) as if they were reviews. An item either marks anticipated becomes generic: it leaves the primary and prints as its own stratum. The screen reads no arm output. Stock row 3 never screens.

**Foreseeable rating.** Each auditor rates each primary item yes, maybe or no: could a careful reviewer with plan.md, context/ and the base code have named this screen and condition? The yes-and-maybe stratum prints beside the primary, and the no-and-maybe items form the harder key that R61's one ceiling raise uses (section 9).

A unit keeps its place only with at least 1 primary item left after the mentioned flag and the generic screen. Drops are counted and reported.

### 3. Units

**Source frame.** The devex eval owns one frame and one public miner for both evals. Its free supply count (2026-11-09, GitHub API only) wrote the frame, and this post freezes it as written: frame-rules.md beside this post copies the frame's rules, the count's mechanical class rules and the exclusion digests verbatim, with the sha256 of each source file. In short:

- **Repositories.** Public GitHub, at least 500 stars, not a fork, not archived, pushed on or after 2026-10-01, under a permissive or copyleft licence by GitHub's SPDX field, found through a dated topic-search union with a developer-facing side and a UI side (web, mobile and desktop strata). It is a lower bound: repositories without topics are missed.
- **Unit.** One merged pull request into the default branch, created on or after 2026-07-01 and merged 2026-07-01 to 2026-09-30 (UTC); not a fix, revert, docs, chore, dependency, release, CI-only, refactor, test-only or translation change by the frame's title and label rule; at least 2 non-test source files or 40 added non-test source lines; at least 120 words of plan text in the earliest recoverable pull request body and closing issues dated before the merge; contained in a release or tag (the miner checks git ancestry); at most 3 units a repository for each eval.
- **Side.** The count's mechanical class rules prefilter. Then a frozen classifier, Opus 5.5 and GPT-6.1 Sol independently with Gemini 4 Argon settling a split, labels each candidate from its title, body, closing issues and changed-file list only: developer-facing, UI (WEB, MOBILE or DESKTOP), both or neither. A unit labelled both goes to the UI side when its UI-file added lines are at least half its added non-test source lines. No unit serves both evals.
- **Draw.** Seed 20261109, order sha256(seed + newline + owner/repo#number). The 14 units the count read in full, and any the devex eval's screen pilot reads, are excluded from both draws.

The classifier's prompt is written once for both evals before any classifier call and lands with the build commit that pins the first paid call; it may read only the inputs above. If the devex eval's merged prereg freezes a frame that differs from frame-rules.md, the difference goes to the Captain before the miner is built.

**This eval's choices, the ones the frame leaves to each eval (frozen here):**

- **Side.** The UI side only, with the class the classifier gives (WEB, MOBILE or DESKTOP) as the unit's surface.
- **Licence.** Both tiers in stages 1 and 2, where repository code can run only inside the offline, keyless review container (section 4): copyleft repositories stay under sealed custody, with nothing redistributed and no network service run. Stage 3 builds and runs the code, so it takes the permissive tier only, as family U planned.
- **Window.** The 60 days after the merge (UTC), as the program plan set. A change released late gives users less time with it, the same for every arm; the release lag prints as a descriptive read.
- **Strata.** No quotas. The frame's count found web scarce under its rules and mobile and desktop dominant, so each surface prints descriptively with its own MDD, and a result speaks to the mix the frame gives.
- **Key screen.** The free screen below, before any paid read.

**Key screen (free, frozen).** The screen runs on a unit only after its 60-day window has closed, so it sees the whole window; a unit whose window is still open waits, and never drops for that. For each drawn unit the miner lists every issue and discussion created, and every pull request merged, in the repository within the window, leaving out authors GitHub marks as bots. It keeps as candidates, in this rule order:

1. *Cross-reference:* an item whose timeline cross-references the unit's pull request or whose body links it.
2. *Blame:* a merged pull request whose changed or deleted lines in UI files (the frame's web, mobile and desktop file tests) blame to the unit's merge, by the eng-review miner's SZZ run on those files.
3. *UI files:* a merged pull request that edits a UI file the unit added or changed and whose title or body holds a UI class word.
4. *Identifiers:* an issue, discussion or pull request whose title or body names one of the unit's identifiers together with a UI class word. Identifiers are the base names of UI files the unit added or changed, at least 5 characters long and not on the frozen stop list (index, main, app, styles, style, utils, helpers, components, component, page, pages, layout, view, views, screen, screens, theme, types, constants, common, shared), and the component, view or screen names the unit's UI files declare (an exported PascalCase function, class or constant, a Swift struct or class, or a Kotlin function marked @Composable).

UI class words, case-insensitive, whole words: loading, spinner, skeleton, empty, blank, placeholder, error, fails, failed, broken, crash, layout, overflow, overlap, cut off, truncated, responsive, mobile, tablet, small screen, orientation, landscape, zoom, safe area, notch, accessibility, a11y, screen reader, VoiceOver, TalkBack, aria, label, focus, keyboard, tab order, contrast, dark mode, light mode, theme, color, colour, font, spacing, padding, margin, alignment, icon, confusing, can't find, cannot find, hard to find, unclear, navigation, back button, hidden, disappears, misleading. At most 40 candidates a unit, in rule order and then by date. A unit with no candidate drops before any paid read and is counted as "no screened aftermath". The screen can miss items whose text names neither the change nor its files, so the key undercounts, the same for every arm.

**Eligibility.** A unit enters only when it is on the UI side, has at least one screened candidate, and keeps at least 1 primary key item after section 2's flags.

A change the devex or eng-review eval has already drawn as a unit is not eligible here, and before authoring the mining thread compares candidates against the sealed task lists in a counts-only custody opening and drops any match, as the eng-review eval does.

**Supply (free, from the shared frame's count, 2026-11-09).** The UI side holds 3,113 licensed repositories (web 2,169, mobile 375, desktop 569; 2,339 permissive). A sample of 35 UI repositories gave 1,628 merged pull requests in the window, 1,472 into the default branch and created in the window, 543 after the title and label filter, 276 with 120 words of plan text and 212 after the size rule. The mechanical rules assigned 76 of those to the UI side (19 capped at 3 a repository, from 8 of the 35 repositories), all released by 2026-10-15; 38 permissive and 38 copyleft. Frame-wide, capped at 3 a repository, the estimate is 1,026 UI units (repository bootstrap 90% interval 512 to 1,604): 577 permissive and 449 copyleft, 882 released by 2026-09-30; by class, desktop 427, mobile 424 and web 176 (0 to 465). These counts come from the mechanical rules; the classifier will move some units across sides. 20% of UI units have a closing issue, 5% opened before 2026-07-01 and 3% before 2026-04-30.

The key, not the frame, is the binding constraint. The count read 2 UI units in full over their windows (no web unit in the sample was released early enough): one had 4 items under this post's classes (2 S, 1 H, 1 R; two from outside users' reports and two from follow-up fixes) and the other had none. On the developer-facing side, 1 of 12 units had any item. So a blind draw might need anywhere from 2 to 12 reads for each keyable unit. This eval answers that with the free screen before any paid read, a paid pilot that measures yield, and a supply stop (start rule 10).

**Unit files.** Each unit has three inputs and a sealed key:

- repo/: the repository at the change's parent commit, as a fresh git repository with one commit and no remote, so tools that call git work and no later history exists in the container (H1). The same export is every arm's code, and stage 3 builds start from it;
- plan.md: the team's plan, from the frozen rewrite below;
- context/project.md: the project as it stood before the change, from the frozen context prompt below;
- key.json (sealed, never mounted): the items of section 2 with class, source, statement, evidence pointers, dates and flags, the files each item touches, and the auditors' ratings.

**Plan rewrite (frozen prompt).** The authoring model (Opus 5.5) sees only the earliest recoverable pull request description and its closing issues, with images and links removed, never the diff, review comments or anything dated after the merge:

> Below is the description of a change a software team made, and the request that led to it if there was one. Rewrite it as the plan the team would have written before building: future tense, the same goals, scope, screens, commitments, constraints and open questions, at about the same length. Keep every decision the description states, including any it makes about states, layout, accessibility or styling. Add nothing it doesn't say: no new features, screens, states, layouts, risks, tests or follow-ups, and no implementation detail beyond what it names. Describe no screenshot. Leave out people's handles, names and email addresses. Output only the plan.

**Context (frozen prompt).** The same model sees the README, docs and design-system files at the parent commit, and plan.md:

> Below are a project's README, docs and design files as they stood before a change, and the plan for that change. ### 5. The closing block, normalization and failures

The template, frozen:

> End your reply with one fenced block labelled plan-changes that holds a JSON object {"changes": [...]}: at most eight changes you would make to this plan before anyone builds it, most important first, each one string of at most 40 words. Only this block is scored.

The template names no screen, state, viewport, user or design system, so the none arm gets no lens from it. The scorer reads the last plan-changes block in the reply, wherever it sits. A skill arm's own outputs (plan.md edits, the Completion Summary, autoplan's findings and revised plan) are exposure evidence only and never scored: every arm is scored on the same block. Normalization, the same for every arm, stock row and oracle list before any judge reads anything: keep the first eight strings; strip markdown (emphasis, code ticks, links, headings) and leading numbering; collapse whitespace; cut each string at its 40th word; render as numbered plain lines. A block can't stay over the caps after normalization, because normalization cuts it. The run reports, per cell, the mean words and items per block and the share of items the cut shortened.

### 6. Judging (R78)

**Who judges which lists.** GPT-6 Astra (openai/gpt-6-astra) labels every list a Claude model wrote (Opus arms). Opus 5.5 labels every list a GPT model wrote (Sol arms). particle-1 lists go to a panel of Astra and Opus, with Gemini 4 Argon (google/gemini-4-argon, through OpenRouter with data collection denied) as the third vote. Each judge's yes labels come with support edges, a change index paired with the key item it matches. The panel's rule: an item is anticipated when at least two judges say yes, and its edges are the ones at least two judges name; when a yes item has no edge with two votes, its edges are the ones Gemini named. Gemini is asked on every item where Astra and Opus disagree on the label or, for a shared yes, name different edges. The one-to-one matching (section 7) runs over the panel's edges only, and each judge's own labels and edges print beside the panel's. Stock rows, oracle lists and shuffled-key packets go to the same judge as the lists beside them. Production label and pairwise calls run at medium reasoning effort, the judge-check pass at maximum. Every result records the judge model, version and effort, and judge calls are cached by model, version, prompt digest and packet digest.

**Labels (primary).** Each packet holds one unit's key items (statements only, with each item's files) and that model's normalized change lists for the unit across arms, plus the three stock rows, shuffled with a seed and labelled only by a random id. For each list and each key item the judge gives two labels and names every change index behind each yes, one or more:

- *anticipated*: one change names, in substance, both the specific screen, component or flow the item records and the specific state, viewport or device, assistive-technology need, point of confusion or design-system element involved, so that acting on that change as written would have prevented the problem or delivered the later fix. A category alone doesn't match ("add empty states to every screen" doesn't match "the invoices tab showed a blank panel while loading"); the right condition on another screen doesn't match; a change that names the screen and condition in other words does.
- *screen hit*: one change names the item's screen, component or flow, whatever its condition (secondary).

The brief gives three generic match and no-match examples written for this post, from no unit.

**Shuffled-key control.** Each list is also labelled against another unit's key from a fixed pool: in stage 1 the calibration units, in stage 2 the comparison units, each pool frozen with its stage's units digest and frozen again, once and before any label, if the harder-key raise narrows the set. The partner comes from a seeded derangement in this order: another unit from the same repository, else from the same surface, else any unit in the pool. The tier used prints per unit, and specificity prints by tier as a descriptive read. Every unit has a partner, because each pool holds at least 12 units. A list's shuffled A measures how far its changes match a nearby change's aftermath rather than this one's.

**The judge check, before any judge number counts.** It must not be circular. The check set is labelled in a separate pass with its own audit prompt, which asks for the quoted change behind each anticipated label, at maximum reasoning effort, by Astra, Opus and Gemini 4 Argon (Gemini at its highest effort, through OpenRouter with data collection denied). Each production judge's check set comes from the stage 1 lists it labels in production, plus known anchors: stock rows 1 and 2 as known-bad lists (the generic screen removed what they match), while stock row 3 is labelled like any list and never counts as an anchor, and one oracle list per calibration unit as known-good, written by a script that turns each primary item into a change naming its screen and condition. Each production judge is scored only on gold cells its own family didn't help define. The Astra judge's gold is the cells where Opus and Gemini agree in that pass, plus the anchors at their known labels; the Opus judge's gold is the cells where Astra and Gemini agree, plus the anchors. The particle-1 panel holds all three families, so it is checked through the two members that label every cell: on particle-1 lists, Astra's production labels are scored on the Opus-and-Gemini gold and Opus's on the Astra-and-Gemini gold, and the panel passes only when both members pass. Each production judge, and each panel member, needs at least 40 gold cells of each class (anticipated and not), with oracle cells counting toward the anticipated class but supplying at most half of it, from at least 40 distinct lists across both classes. Anchor cells count toward those floors, but in the gate's numbers they are weighted down to carry at most a quarter of the total weight, so easy cases can't pass the gate; the unweighted numbers and the numbers on real lists alone print beside them. Each production judge (Astra on Opus lists, Opus on Sol lists, the panel's two members on particle-1 lists) is then scored on its own gold cells from its own production labels: its catch rate on bad outputs, its false-fail rate on good ones and Cohen's kappa. Kappa of at least 0.6 is needed before that judge's contrasts can return any verdict. A judge under 0.6, or short of gold cells, makes only its model's contrasts read untested (judge); only the Opus-list judge's failure ends the eval (section 9). Gold cells print by arm and by class. **The stage 2 re-check, with its own sample.** Each production judge gets 80 gold cells again in stage 2: 40 of each class, drawn from its stage 1 gold set stratified by arm (for the panel, 40 from each member's set, each member scored on its own 40), from at least 20 distinct lists, with anchor cells weighted to carry at most a quarter of the weight as above. The stage 1 gold cells are reused on purpose, because stage 2 has no second gold-labelling pass; the judge meets them only inside fresh packets. They reach the judge in 8 gold packets of 10 cells, spread evenly through its stage 2 batches, formatted like any packet and labelled only by random ids. Each judge's catch rate, false-fail rate and kappa on those cells print beside every stage 2 result from its lists, with the same gate: a judge under 0.6, or short of gold cells, leaves its model's stage 2 contrasts untested (judge) (section 10). A seeded subset of 40 gold cells per family is kept in a plain rendering, so the owner could label it if this eval heads to a public post; nothing asks him to now.

**Pairwise plan quality (secondary, decides nothing).** For pass 1 of each unit, the judge sees plan.md, context/project.md and two normalized blocks in random order: each gstack arm's against none's, each against the lens's, and a stock block (stock rows 1 and 2) against none's. It answers which set of changes would leave the shipped screens with fewer missing states, layout and accessibility problems and less user confusion, or tie, with one sentence why. No key is shown. The same family rule applies. Pairwise runs on Opus and Sol blocks only. The stock block must win at most 20% of its pairs against none on Opus; above that, the pairwise read is flagged untested (stock).

### 7. Scoring and volume controls

**Primary, per review: A = credited primary items divided by the unit's primary items.** Credit takes a maximum one-to-one matching between the eight changes and the key items over every change index the judge named, so one change earns at most one item. A unit-pass's A is that share; units weigh equally.

**Secondaries, all from the same labels or mechanical reads:** A by class (S, H, R, A, Y) and by source (user report, fix); the screen-hit share; per-change precision (the share of changes credited with any item) and the specificity score (A minus shuffled A), per arm and as the difference in differences against none; A on mentioned and generic items and the foreseeable stratum; a mechanical file read (the share of items whose files the changes name by path or component name); the length-adjusted difference; and pairwise plan quality, raw and length-controlled.

**Volume can't win.** Eight changes of 40 words, normalized before judging; one-to-one credit; the specific-match rule; the generic screen; the shuffled-key control; and three stock rows judged in every packet as if they were reviews. The stock rows, frozen:

- **Row 1, generic UI advice:** (1) Add loading, empty and error states to every screen that fetches data. (2) Make every new screen responsive and check it at phone, tablet and desktop widths. (3) Meet WCAG 2.1 AA: labels on every form field, alt text on images and 4.5:1 text contrast. (4) Make every interactive element reachable by keyboard with a visible focus ring. (5) Use the existing design system's components, colours and spacing tokens instead of custom styles. (6) Give each screen one clear primary action and a visible way back. (7) Show clear error messages next to the field or action that failed. (8) Handle long names, missing images and zero results without breaking the layout.
- **Row 2, generic process advice:** (1) Make wireframes or mockups of every new screen before building. (2) Run a usability test with five users before launch. (3) Get design sign-off from the product owner before implementation. (4) Write a design spec that covers every screen and interaction. (5) Add visual regression tests for the new screens to CI. (6) Test the feature on real phones and browsers before release. (7) Run an automated accessibility audit such as axe in CI. (8) Document the new components in the design system or Storybook.
- **Row 3, the skill's own checklist (never used to screen):** (1) Add a table of loading, empty, error, success and partial states for each feature, saying what the user sees in each. (2) Define what the user sees first, second and third on each screen, with one primary action. (3) Add a storyboard of the user's journey: what they do and feel at each step. (4) Specify each viewport's layout, not just "stacked on mobile". (5) Specify keyboard paths, ARIA landmarks, 44-pixel touch targets and contrast. (6) Use the tokens and components in DESIGN.md and check each new component against them. (7) Replace generic patterns (three-column icon grids, gradients, everything centered) with specific choices. (8) Make empty states features, with warmth, a primary action and context.

**Consistency and stock checks.** Rows 1 and 2 should anticipate no primary item after the screen, so their count is a consistency check on the judges. Row 3 guards against the skill's own generic moves. Stock fail reads per production judge and model: a model's stage reads STOCK FAIL when any one row is credited with a primary item on more than 2 of the 16 calibration units (stage 1) or on more than one comparison unit in eight (stage 2: more than 8 of 64 at the planned size). A row counts a unit when that model's judge credits it with a primary item in at least one of the unit's production packets with its own key on that model (one a pass), and it counts the unit once however many of those packets credit it; shuffled-key packets and the judge-check pass never count. In stage 1 a stock fail on Opus lists ends the eval, and one on Sol or particle-1 lists makes that model's contrasts read untested (stock); in stage 2 a stock fail makes only that model's contrasts read untested (stock). Row 3's credits print per arm and model either way.

**Length.** Beside each primary, a length-adjusted difference: the unit difference in A regressed on the difference in the two arms' list word counts, each arm's A and word count a mean over its scored passes, with the intercept and its cluster-bootstrap interval. It is a sensitivity read, never the verdict.

### 8. Attacks on the scores, answered before code

1. *Volume and verbosity.* The 8-by-40 cap, normalization, one-to-one credit, the stock rows, per-change precision and the length-adjusted read.
2. *Generic hits.* Design advice is easy to state generically ("add empty states"), so this is the eval's main risk. The specific-match rule (screen and condition both), the generic screen, the shuffled-key control and the stock checks, including a row built from the skill's own checklist.
3. *Self-preference.* No model judges its own family's lists; particle-1 gets a three-family median.
4. *A judge that labels badly.* The non-circular judge check with known-bad and known-good anchors, kappa of at least 0.6 to gate, and a blind stage 2 re-check.
5. *Style revealing the arm.* The skill's tables and pass names could tip a judge. Normalization strips formatting, and labels are factual matches against a key. A descriptive probe asks Astra to guess the arm of 30 random lists; above 70% correct, the post flags it.
6. *Blame noise in UI files.* Key writers confirm every fix by reading it beside the change, auditors recheck it, and the pilot prints the share of blame candidates the key writers kept (section 3).
7. *Hindsight.* Many UI problems only show in use. The headroom band's floor catches a mostly unforeseeable key, and the foreseeable stratum prints.
8. *Echoing the plan.* Mentioned items leave the primary.
9. *Leaks.* Inputs come only from material dated before the merge; the container holds no later history; the window starts after Opus 5.5's stated cutoff; web tools are denied; each model's own cutoff is checked, and Opus's possibly later data gets a strict stratum, a by-month print and a recognition probe (section 10).
10. *Big changes dominate.* Units weigh equally with at most 6 primary items each; A prints by change-size tercile.
11. *The format is the lift.* Every arm writes the same block, so no arm wins by being the only one asked for design changes; the lens arm and the stock rows test how much the framing alone carries.
12. *Effort, not procedure.* Skill sessions read more and take longer. That is the procedure's mechanism, so it counts, and cost per credited item prints beside each contrast.
13. *Failures scored as misses, or dropped in an arm's favour.* Section 5's table: failures outside the agent are missing, never 0; stops the arm causes score 0 after one retry, with a sensitivity read; a contrast with more than 10% missing in either arm reads untested.
14. *Silent reporting.* Many UI problems are never reported or fixed within 60 days. The key undercounts the same way for every arm, and the null wording says what the key can't see.
15. *Autoplan without its design lens.* gstack decides UI scope; if it misses a UI plan, the reviewer gets no design lens. The keyless scope read prints first, and the detector counts such a run as unexposed for this eval, so autoplan's verdict is about what it actually loads.

The reads come in this order, and the first that fires decides: NO READ (the Opus-list judge short of gold cells or under kappa 0.6, or the parse rate under 95%), then STOCK FAIL on Opus lists, then the band. FLOOR (A under 0.10) is FIX-METHOD on task fit: these UI aftermaths are mostly unforeseeable from a plan, and stage 3's build read becomes the next attempt's primary. When the Opus-list judge falls short of anticipated gold cells the eval reads NO READ whatever A is; the post may name a low A as a likely floor but never claims FLOOR. Why these edges: the shared design sets the band at 0.10 to 0.65; with 1 or 2 items a unit, 0.10 is about one item in seven units, and 0.65 leaves room of 0.35, about three times the 12-point smallest effect worth acting on. Stage 1 prints A with its 95% interval (power.txt part F: a half-width of about 0.10 to 0.20 at 16 units), but the band reads the point estimate.

**CEILING and R61's one raise.** CEILING is A above 0.65. It doesn't end the eval at once: the one ceiling-raise attempt R61 asks for runs first, at no new cost. The primary narrows to the harder key, the primary items neither auditor rated foreseeable yes, which the auditors fixed before any arm output existed (section 2). Opus none's A on the harder key is read from the same stage 1 labels, on the calibration units that keep at least one hard item (at least 12, or the raise fails). HEADROOM on the harder key, with the same band, stock and judge rules, admits stage 2 with the harder key as its primary, named that way in every headline, and the comparison set keeps only units with a hard item (start rule 6's admission read and start rule 10's floor of 48 apply). Anything else after the raise ends the eval as R48 FIX-METHOD (saturation): plain Opus already plans for these problems. No CUT-CANDIDATE comes from stage 1, or from this eval at all (section 10).

**Smoke rules (D1), fixed now.**

1. *Parse.* Each gstack arm must return a parsable block in at least 5 of its 6 smoke sessions on a model.
2. *Exposure.* Each gstack arm must be exposed (section 4) in at least 5 of its 6 smoke sessions on a model.
3. *Cost.* The smoke's measured mean cost per session replaces the planning figure for that arm and model in the projection rerun (section 13).
4. *The one repair.* An arm that fails rule 1 or 2 on a model reruns its 6 sessions on that model with the harness's Stop hook: gstack-evals code that runs that arm's detector and the block parser when the session tries to stop and, while the procedure hasn't shown or no block parses, blocks the stop with one fixed message naming the missing outputs, at most twice. For autoplan the same hook also answers the gate, as it always does. D1's listed repairs don't apply here: the forced sentence is already in every gstack arm's prompt, and plan-design-review has no opt-in gate. An arm that passes rules 1 and 2 on the re-smoke runs on that model "with an enforced procedure", named so in every headline. An arm that fails again drops for that model: its stage 2 cells there don't run, its contrast reads untested (exposure or parse), and the results say so. Blocks print per session.
5. *Lens.* At least 95% of each model's stage 1 lens reviews must parse; otherwise the template goes to the Captain before stage 2.

### 10. Stage 2: the comparison

64 comparison units, or the count section 3's re-sizing leaves. Opus 5.5: all four arms at 2 passes. Sol and particle-1: all four arms at 1 pass. Each unit's cells run interleaved in a seeded order.

**Primaries, per model (F1):** plan-design-review minus none, and autoplan minus none, with Holm across the two. The Holm family is frozen at those two: an arm that doesn't run or stops (a smoke drop, an interim exposure stop) enters with p = 1. A unit's arm score is the mean over its scored passes (section 5); differences pair by unit and cluster on the repository, because the frame allows up to 3 units a repository (the repository is taken from each unit's record, checked so the cluster count equals the repositories left after section 5's drops); each difference has a 95% repository cluster-bootstrap interval (10,000 draws, seed 20261109) and a two-sided repository sign-flip p, which flips each repository's units together. Every comparison prints paired, with its interval and the count of units whose A got worse.

**Secondary contrasts (decide nothing on their own):** lens minus none; plan-design-review minus the lens and autoplan minus the lens (whether the one-line framing carries the gain); plan-design-review minus autoplan; and every section 7 secondary per arm.

**Verdict precedence, fixed now.** For each gstack arm and model, the first rule that holds gives the reading:

1. **Stage 1 ended the eval** (NO READ, STOCK FAIL on Opus lists, FLOOR, or saturation after the raise): every contrast reads that outcome, and nothing below is read.
2. **Incomplete** on that model: a cap stop on that model's stage 2 runs item or on the judge item, a provider change (E_DR_PROVIDER_DRIFT), or any other stop code that halts that model's stage 2 cells before every planned cell ran. Every contrast on that model reads incomplete, with the reason, and its partial estimates print as descriptive only. A stop that halts only one arm on that model (a smoke drop, the interim exposure stop) is read by the steps below.
3. **Dropped at smoke** on that model: untested (exposure) or untested (parse), named with the repair tried.
4. **untested**, when any of these holds, each named: (judge) that model's judge under kappa 0.6 or short of gold cells, in stage 1 or in the stage 2 re-check; (stock) a stock fail on that model's lists; (leak) more than a quarter of the model's units leak-exposed; (exposure) the arm's exposure under 0.80, or the interim stop; (coverage) more than 10% missing in either arm of the contrast; (contamination) more than 5% of the none sessions on that model read a gstack file.
5. **helps** (or **hurts**): Holm p at most 0.05, the interval excludes zero, and the specificity contrast has an interval that excludes zero in the same direction. The specificity contrast is the paired difference in differences per unit, (A_arm minus shuffled A_arm) minus (A_none minus shuffled A_none), with the same cluster bootstrap.
6. **not shown**: an interval that excludes zero but fails Holm or the specificity contrast. It prints with the requirement it failed.
7. **no measurable difference**: the interval includes zero. The MDD and the interval print with it.

**Interim exposure stop:** after the first 24 Opus sessions of a gstack arm in stage 2, an arm with exposure under 0.70 stops; its cells read untested and its remaining cap is released.

**Leak exposure (B1).** Before stage 1, the build records each model's stated training cutoff from its provider's documentation (the product-value eval's cutoffs.json: Opus 5.5 June 2026, GPT-6.1 Sol 2026-04-30, particle-1 none published, which the Captain ruled a stated limit, not a cutoff). A unit whose earliest exposure falls before a model's stated cutoff is leak-exposed for that model: descriptive, out of that model's primaries; a month-stated cutoff covers the whole month. If more than a quarter of a model's units are leak-exposed, its primaries read untested (leak). The merge window starts after both stated cutoffs, and the frame's count puts the earliest exposure of about 5% of UI units before 2026-07-01 and 3% before 2026-04-30, far under a quarter; the check runs anyway. For Opus's possibly later data (the repository's earlier records note data possibly collected to September 2026, unverified), A prints by merge month, a strict stratum of units first exposed on or after 2026-08-01 prints beside every Opus primary, and a descriptive recognition probe asks Opus none, on each calibration unit, what changed in the project's UI in the 60 days after the merge; units it recognizes print as their own stratum.

**Reading rule, fixed now.**

- **KEEP** for a gstack arm on a model needs that arm minus none to read helps. It is worded "its plan changes name more of the screens and conditions where real UI problems later landed". It is flagged, not changed, when the pairwise secondary shows the arm losing (a length-controlled win rate below 0.5 with an interval that excludes 0.5), or when stage 3 shows that arm's builds passing fewer aftermath checks than the none block's builds, with an interval that excludes zero.
- **The one-line framing carries it** is written only when the arm minus none helps and the arm minus the lens has a 95% upper bound below +0.05. When lens minus none helps but the arm minus the lens doesn't meet that bound, the post writes that the framing carries part of the gain, which is no lead to cut.
- **No CUT-CANDIDATE from this eval.** DES-7 is scored by no planned eval and DES-8 waits for wave 2, so the program's rule (every main intention scored somewhere) can't be met. - **The two arms are read apart (F1).** The skill's verdict is about plan-design-review; autoplan's is about autoplan's default run and its design lens (inventory intention AP-DES-1). Neither verdict borrows from the other, and plan-design-review minus autoplan is a secondary.
- Any null covers naming the screens and conditions where real UI problems later landed. It does not cover the look (DES-4), mockups (DES-7), the person's decisions (DES-8), or what ships (stage 3 reads that descriptively).

### 11. Stage 3: the build-level reads (descriptive)

Stage 3 asks the claim's second half directly: does a plan reviewed by each arm lead to screens that handle their states, layouts and accessibility, avoid the real later problem, look specific and let a user finish the job? It folds in family U's agent user on frozen tasks. It is descriptive and decides nothing except the KEEP flag above. It runs after stage 2's Opus pass 1 exists, whatever stage 2's verdict.

**Stage 3 units.** Up to 16 comparison units, tried in the draw order (at most 24 tried), among units that: sit in the permissive tier; render their changed screens in a headless browser, as a web app, a desktop app whose interface is a web renderer (Electron or Tauri) or a mobile app with a working web target; install, build and serve those screens in the stage 3 sandbox at the parent commit and at the merge from a frozen recipe; have at least one validated aftermath check; and have three valid agent-user scenarios. Native mobile and desktop screens can't render in a headless browser, so stage 3 reads web-rendered screens only. With web scarce in the frame, fewer than 16 may qualify: stage 3 then runs on those that do, and with fewer than 8 it doesn't run, its caps are released and the post says so.

**Stage 3 authoring (sealed, per unit).** Opus 5.5 writes, from the real merged change and its key, and GPT-6.1 Sol audits:

- the recipe: install, seed data, start command, base URL, and the routes or deep links where the change's screens appear, with the seed that reaches them;
- fixtures: for each data request the change's screens make, an empty response, an error response (HTTP 500 in the backend's error shape) and a held response, applied through the browser's request interception; for apps with local data, the matching seed states;
- aftermath checks, one per key item a mechanical check can tell: for S, the forced state and an assertion that the screen shows a distinct, non-blank state with no uncaught error; for R, the viewport and an assertion (no horizontal overflow, the named element inside the viewport); for A, the axe-core rule on the named element, or a keyboard-reach assertion; for Y, a read of the build's diff for the hard-coded values the real fix replaced; for H, a DOM assertion (the element the real fix added or moved is present and visible). A check counts only when it fails on the real merged tree and passes on the real fixed tree, twice each;
- three agent-user scenarios: a goal a user should be able to reach with the change, and a state checker (a stored record, a URL, a DOM state). A scenario counts only when the agent user completes it on the real merged tree.

**Build arms.** Six per unit, 1 trial each, all by Opus 5.5 in Claude Code with no gstack: plan.md alone (no review); plan.md plus each review arm's normalized block from its stage 2 Opus pass 1, or pass 2 when pass 1 has none (none, lens, plan-design-review, autoplan); and the generic-look control, plan.md plus a frozen stock block that asks for the look the skill calls generic: "Style any new screen the way most AI-built apps look: a centered layout, a purple-to-blue gradient header, a grid of three cards each with an icon in a coloured circle, large rounded corners on everything, and the system font stack." The prompt: "Implement the plan in plan.md in /work/repo. A reviewer's notes on the plan follow; use them as you see fit." then the block. Session limits: $15, 250 turns and 120 minutes. A review arm with no Opus block for a unit (a smoke drop, the interim stop, a no-block reply or a missing session) doesn't build on that unit, its cap share is released, and its readouts pair only units where both builds exist, with the count printed.

**The sandbox (I1).** One throwaway Ubicloud VM per build run and per check run, deleted after. It holds no keys: the builder's model calls go through the metering proxy on the controller host, which keeps the key and admits only Opus 5.5 on that run's lease. Egress goes only to the proxy and a package mirror (a pull-through cache on the controller host for the unit's package managers, its configuration pinned by digest). No drive or host directory is mounted. The app and a headless Chromium run inside the VM on loopback, and the controller drives the browser through Playwright's remote protocol over the VM's SSH tunnel, so the agent user's and the judges' model calls come from the controller and no key enters the VM. After each run, an audit records the VM's processes, its egress log and the files written outside /work.

**Measures, per build.**

1. Build and serve: the build's tree installs and starts with the unit's recipe and serves every route.
2. Accessibility: axe-core (version pinned at the build) serious and critical violations per route at 375 by 812, 768 by 1024 and 1440 by 900 pixels, and the new ones against the no-review build.
3. Responsive: horizontal overflow at 375 and 768 pixels, and interactive elements under 44 pixels on the changed screens at 375 pixels.
4. Forced states: for each route and each of empty, error and loading, whether the screen shows a distinct state, by a mechanical read (no uncaught page error, a non-blank main region, a loading indicator by role, aria-busy or text within 1.5 seconds) and by Astra reading the screenshot blind (a designed state, blank, broken, a raw error, or a spinner that never ends).
5. Aftermath recurrence: the share of the unit's validated aftermath checks that pass on the build.
6. Agent-user completion (family U): GPT-6.1 Sol, from a family other than the builder's, as the fixed agent user, with a screenshot and the accessibility snapshot each step and a 25-step cap; completed scenarios over 3; steps, failed actions, console errors and dead ends (a state seen two or more steps earlier) as secondaries. The agent user never sees the plan, the code or the arm. An app that doesn't start scores 0.
7. Design-system fit: colour and spacing literals the build added in UI files where the project has tokens.
8. DES-4 pairwise: each of the five non-control builds' desktop and phone screenshots of its main changed route against the generic-look control's, in random order, judged blind by Astra and by Gemini 4 Argon, both from families other than the builder's: which screen looks designed for this product and its users rather than a generic template, or tie. Each arm's win rate against the control prints, with both judges' rates. Instrument check: the no-review build must beat the control in at least 70% of its pairs, or the DES-4 read is flagged (instrument).

**Failures.** A build that stops on its own limit gets one fresh retry under section 5's arm-stop rule, and the retry is measured as it stands. A build that doesn't install or serve is its own endpoint (measure 1): its render reads (axe counts, overflow, target sizes, forced states, aftermath recurrence, design-system literals and the DES-4 pairwise) are unavailable, never zero, and its unit leaves those paired readouts, with the counts printed; its agent-user completion scores 0, since no user can finish a task in an app that doesn't start; a failure outside the agent gets one retry under J1, then the build is missing; an agent-user or judge call that fails is retried once, then that scenario or read is missing.

**Readout.** Every measure paired by unit against the none-block build and against the no-review build, each with a 95% cluster-bootstrap interval and the count of units that got worse.

### 12. Power and MDD

power.py (attached; seeded, no key, no network) simulates the primary: unit difficulty from a Beta distribution, items around their unit, a control calibrated so its mean item rate is the stated rate, the arm's lift as a logit shift with unit noise and a repository effect (solved so a true zero has no lift), units in repositories of 1 to 3 as the frame's UI sample had them, separate pass counts for the arm and for none, and a two-sided sign flip on repository sums. Its planning output is power.txt (attached). An MDD row comes from 1,000 simulated runs, so neighbouring rows can differ by 0.01 from Monte Carlo error alone.

- **At the planned size,** 64 comparison units with Opus at 2 passes, the Opus MDD at Holm's first step (alpha 0.025) is 0.12 when Opus none sits at 0.20 with 1 or 2 key items a unit, and 0.13 at 0.35 (ICC 0.5). With 2 to 4 items a unit it is 0.09 and 0.10. The one keyable UI unit in hand had 4 items, but one unit binds nothing, so the 1-or-2 row is the planning row.
- **The admission read is tighter than the MDD rows.** It asks for power of at least 0.80 at a lift of 0.12, from 4,000 runs with fixed seeds on one layout, and prints its Monte Carlo error (part G). At 64 units with 1 or 2 items a unit it gives 0.785 (standard error 0.006) at a control rate of 0.20 and 0.685 at 0.35, both under the bar. With 2 to 4 items it gives 0.991 and 0.966, and 0.934 and 0.859 at 48 units. So the planned size passes only if real keys run richer than 1 or 2 items a unit; if they don't, the set must grow within the line or the question goes to the Captain (start rule 6). The cut of the gstack arms' second pass (section 13) passes at 64 units with 2 to 4 items (0.944 and 0.884) and fails with 1 or 2.
- **The size the MDD rule needs** (at most 0.12, the smallest effect worth acting on): 64 units at a control rate of 0.20 and 80 at 0.35 with 1 or 2 items; 40 and 48 with 2 to 4. Below 48 even the richer item mix misses the rule at 0.35, which sets the supply floor.
- **Sol and particle-1** run 1 pass: their MDD at Holm's first step is 0.17 to 0.18 at 64 units with 1 or 2 items, and 0.11 to 0.13 with 2 to 4. Their contrasts can show only large effects, and the post says so.
- **Surface cells** are descriptive: an MDD of about 0.36 to 0.37 at 16 units, 0.23 to 0.24 at 24 and 0.18 to 0.19 at 32.
- **Stage 1's headroom read** on 16 calibration units at 3 passes has a 95% half-width of about 0.10 to 0.20 across the band.
- **The +0.05 bound** is descriptive here (section 10): at 64 units a true zero lands below it in about 29% to 43% of runs with 1 or 2 items and 47% to 64% with 2 to 4, so a null will often not clear it.
- **A repository effect** of twice the planning value moves the 64-unit MDD by at most 0.01.

**The admission read on the measured design (frozen).** Before stage 2 the run thread writes design.json from the authored comparison set: each unit's repository digest and its count of primary items (1 to 6), stage 1's Opus none A as the control rate, ICC 0.5, and the pass counts the arms will actually run (2 and 2 as planned, or 1 for the gstack arms and 2 for none after that cut). It runs `power.py --design design.json` at the build's pinned commit. The read passes at power of at least 0.80 for a lift of 0.12 at Holm's first step (start rule 6); its line prints the power, its standard error and the inputs. The file holds only digests and counts, and lands with the results.

### 15. Custody, outside terms and public safety

Units, keys, judge labels, stage 3 recipes, fixtures, aftermath checks and scenarios, and every review and build stay sealed in the Captain's drive with committed digests only. Everything is decrypted in /dev/shm under the custody rules, and every machine that touched sealed material gets the plaintext sweep at each seal and at the end. Stage 3 sandboxes receive only the unit's repo/ export, its plan.md and its block, never a key. A published key would let later models train on the answers.

**A dated terms record** is written before the cap request and kept with the run record: the provider each model runs on, its data retention and training settings as read that day, the package mirror's registries and their terms, Ubicloud's terms, and the basis for sending repository, issue and pull request content to each model provider (public content, processed for evaluation and never republished). MPL-2.0, which the frame counts as permissive, is a weak copyleft licence whose conditions attach to distributing its files; stage 3 distributes nothing.

**Outside terms, licences or rights.** GitHub's terms of service and API limits for mining (public data, paced GraphQL, no scraping past limits), and its acceptable-use rules on personal data: plan rewrites leave out people's handles, names and emails, and key statements name no person. Repository licences: the permissive ones allow copying and running the code for evaluation; the copyleft ones attach their conditions to distribution, and AGPL-3.0 also to letting users interact with a modified copy over a network. Nothing is redistributed or published. Repository code runs only inside the offline review containers and stage 3's sandboxes, never as a service anyone else can reach, and stage 3, limited to the permissive tier, runs builds only on a sandbox's loopback for our own browser. Bundles stay sealed, plans are rewrites, and key statements are our own words; issue and commit text is summarized into sealed statements and never published. Model terms: OpenAI's API terms for Astra; OpenRouter's terms, with OpenAI as the pinned provider, for every Sol call (arms, the classifier, the second auditor, stage 3's audits and agent user); Anthropic's commercial terms for every Opus call (arms, judges, the classifier, rewrites, context, keys, the first auditor, stage 3 builds and authoring); OpenRouter's and each serving provider's terms for particle-1 and Gemini (a judge vote, the classifier's split and the DES-4 pairwise), with data collection denied; and Claude Code's own terms, which cover it as the harness when it drives Sol and particle-1. gstack is MIT at its pin. axe-core is MPL-2.0 and runs unmodified as a tool; Playwright is Apache-2.0; Chromium is BSD-style. The package mirror only caches public packages under their registries' terms. Ubicloud's terms cover the VMs, each deleted after its run.

### 17. Risks, limits and not in scope

- Many UI problems are never reported or fixed within 60 days, and blame finds a fix only where it touched the change's own lines. The key undercounts, the same for every arm.
- A follow-up UI change reflects what a team chose to fix, not every problem users met.
- Plans are rewrites of what a team wrote while building, often after the screens existed; the frozen rewrite drops screenshots and adds nothing, and the plan's own design decisions stay in.
- Every gstack arm runs unattended and without web tools; plan-design-review was written for a person at the keyboard, and its mockups and decisions (DES-7, DES-8) can't show here.
- autoplan's arm is the lean run with a 28-line design checklist, not autoplan's full design phase (O1).
- Judges are single models per arm under R78; the judge check and its stage 2 re-check are the guard.
- Opus 5.5 may hold data collected to September 2026, which covers the merge window; the strict stratum, the by-month print and the recognition probe bound that but can't rule it out.
- Stage 3 reads web-rendered screens of permissive units only and builds one trial per arm, so it may read fewer than 16 units, leans toward web and desktop web views, and its reads are descriptive and noisy.
- The frame's count found web scarce and mobile and desktop dominant, so the comparison set will be mostly mobile and desktop changes, and a result speaks to that mix.
- Key yield is unknown: the frame's full reads found an item in 1 of 2 UI units and 1 of 12 developer-facing ones. A low yield shrinks the set (section 3), and below 48 units the eval stops for the Captain.
- Not in scope: design-review (it stays on family U as that plan approved it), autoplan's full form, the interactive skill, editing gstack's code, posting anything, and any parity claim.
