# Preregistration: does gstack's design plan review make a plan carry the design decisions its product's own evidence supports?

## Approval

The project owner chose this design (option F1 of the re-plan) on 2026-11-14: constructed product units on 16 to 20 real permissive web apps, about $3,350 all-in inside the eval's $4,000 line, with no GitHub mining. The Captain then set this post's brief: the plan-mode intentions rule, the product-value rule, R78's judge and reporting rules, a no-gstack arm and the three models under test, an admission check before the comparison, gates tested on known cases before any paid pilot, spare twins, a 2x and a 10x tier at a flat cost per session with a headroom check each, and every paid item capped inside $4,000. This post's own review, under R65's path for a paid-eval preregistration, was one lean /autoplan run (autoplan-20261113233829) with one reviewer reading the plan and its draft files. The Captain answered its gate and took every recommendation; those changes alter no cap, arm or design choice, so they weren't taken to the project owner (Review record). This post approves no item's spend: no paid call runs until it merges and the Captain records each item's cap.

## ELI5

gstack has a skill, plan-design-review, that reviews a plan the way a senior product designer would, before anyone writes code. It is meant to make the plan say exactly what people will see and do: what comes first on each screen, what the screen shows while it loads, when it is empty and when something fails, how it works on a phone and with a screen reader, and how it fits the design the app already has. Our first plan for testing it used what really happened after real UI changes shipped. A sibling eval that used the same method couldn't build a single usable answer key from 62 real changes, mostly because of how its key check was built. So this test builds its cases on purpose. We take 16 to 20 real open-source web apps, each with its own components and styles. For each case, a model from outside Claude's family invents one new screen the app's team might plan, writes the plan the way a team would, and writes the product evidence the team already holds, as ordinary files in the repository: support summaries, user research notes, analytics, API notes, a customer's requirement. That evidence quietly supports five design decisions the plan leaves out, one each about states, what users need first, phone layouts, accessibility and reuse of the app's own components. A case stays only when three frontier models handed the evidence all reach those decisions, and a decision drops when any of them names it from the plan alone, so the answer key is what the evidence supports, not what anyone can guess. Each reviewer gets the plan and the app's code with the evidence inside it, and writes up to eight short changes to the plan. A change scores when it names the screen and the exact condition. We compare four setups on Opus 5.5, GPT-6.1 Sol and particle-1: no gstack, a one-line "senior product designer" prompt, the skill, and autoplan's default run. A 2x and a 10x harder version of each calibration case, at the same cost per session, guard against a test plain Opus finds too easy. Judges come from a different model family than the model judged, and they are checked against known answers before any number counts.

## Before → after

Before: plan-design-review has eight main intentions and none is scored. The real-aftermath preregistration (2026-11-09-geva-420) is on hold and can't start: it waits for a devex stage 1 reading that won't come, and the devex eval, which shares its frame, miner and key method, stopped with no usable key from 62 screened changes.

After: a frozen test whose answer key is the set of design decisions a screen's hidden product evidence supports, on real web apps whose code every arm reads. It reports, per model with paired intervals, whether plan-design-review and autoplan's default lean run each name more of those decisions than the same model with no gstack and than a one-line product-designer prompt. A headroom check on three difficulty tiers runs first, a judge check gates every verdict, a twin check tests that the score doesn't depend on the case's surface, and a build stage on up to 16 units shows what ships, descriptively. It scores the same six main intentions as the plan it replaces and names the two it leaves untested.

## Why it matters

plan-design-review loads in every interactive design review and, as a short checklist, in autoplan's default run whenever a plan touches UI, so most UI plans that go through gstack meet some form of it. If it makes plans carry the decisions a product's evidence calls for, builders should keep it and autoplan should carry more of it. If plain Opus already writes them in, the procedure costs time and tokens for nothing. Today nobody knows, and the crew's rule forbids a cut while a main intention is untested.

## What caused this work

The devex eval stopped with 0 of 62 screen-positive changes keyed (wiki board post 2026-11-12-geva-484-devex-supply-results). A re-plan for this eval's keys found the main cause in how the devex key audit was built: auditors were asked to check rules against material they were never shown, and one problem from either auditor failed the whole unit. Keys tied to a change only by text were the second cause. Real aftermath keys also floored the eng-review intentions eval: plain Opus 5.5 named 0.087 of its key (2026-11-11-geva-434-eng-review-intentions-stage-1-results). The re-plan offered four options. On 2026-11-14 the project owner took the recommended one: constructed product units on 16 to 20 real permissive web apps, inside this eval's $4,000 line, with no GitHub mining. The Captain then asked for this superseding preregistration, with a 2x and a 10x tier, spare twins, gates tested on known cases before any paid pilot, and every paid item capped inside $4,000.

## Big decisions

1. **Units: constructed screens on real apps, a reversal of P1.** Options: (a) real UI changes and what users later reported, as 2026-11-09-geva-420 planned; (b) invented screens planned on real permissive web apps, keyed to hidden product evidence placed in the repository; (c) grading only what ships. Pick (b), as the project owner did. Why: (a) depends on a key method that keyed 0 of 62 units in devex and floored in eng-review, and on a GitHub miner that stalled on the shared identity; (b) builds the key and its headroom on purpose and keeps real code, which every arm reads; (c) costs past the line and has no MDD we can size. What it costs: the claim narrows from "the UI problems users later hit" to "the design decisions the product's own evidence supports", and every headline says so. What would flip it: a key method for real aftermaths that passes its gates on known cases.
2. **The key and its two drop rules.** Each unit's author writes five key items, one in each class (S states, H hierarchy and navigation, R responsive, A accessibility, Y design-system fit). An item stays only when Opus 5.5, GPT-6.1 Sol and GPT-6 Astra, each handed the plan, the context and every evidence file, all name it (unanimous), and drops when any of the three names it from the plan and context alone (not given away). A unit stays with at least 3 primary items. Per-item drops, not unit drops, follow the devex lesson: drop a bad item and keep the unit while enough items survive.
3. **Audits built the way eng-review built its own.** Two auditors from two families see exactly what the author saw, plus every field a rule depends on, and give each item keep, fix or drop. An item either auditor drops leaves the key; only a problem in the unit's inputs (a signpost, advice in an evidence file, a date after the plan, a real person's name) fails the unit, which gets one rewrite.
4. **Gates tested on known cases first.** Before any paid pilot, every gate that can drop a unit or an item runs on planted known-good and known-bad cases, and a keyless check confirms that a unit obeying every authoring rule passes every keyless gate. A gate that never passes is broken, not strict.
5. **Difficulty tiers at a flat cost per session.** Every calibration unit also exists at 2x (each key item's evidence split across two files, plus a decoy) and is read at 10x (the 2x content scored with a graded rule that also asks for the evidence's specific value, threshold or component). Each tier gets its own headroom read in stage 1, under the difficulty ladder's budget anchor. Stage 2 runs on the easiest tier that reads in band; harder tiers are this eval's ceiling-raise attempts under R61.
6. **Twins, with spares.** Second skins of calibration units, moved onto another base app by the other author family, test that the score doesn't depend on the case's surface. Office-hours' second skins written by the other family failed its unanimity check in 3 of 5 tries, so this eval writes up to 16 second skins to get 8 passing pairs.
7. **Models, arms and size.** Opus 5.5, GPT-6.1 Sol and particle-1 each run all four arms (R54), as in the plan this replaces. 16 calibration units and 64 comparison units on 16 to 20 base apps, Opus at 2 passes and the other two at 1. power.txt puts the Opus MDD at Holm's first step at the planned design in section 12.
8. **No cut can come from this eval.** DES-7 (approved mockups settle the look) needs gstack's compiled designer binary and an image key, which no arm's container holds; DES-8 (the user decides each change) waits for wave 2's owner-control eval. So a null reads FIX-METHOD on task fit, never CUT-CANDIDATE.
9. **The unit builder comes after this post merges.** Every authoring prompt, check and threshold is frozen here, so this post can be frozen without the builder. The builder is planned as the next step, reusing the office-hours lane's authoring code where it fits.

## Implementation plan

### 1. The question, the claimed value and construct fit

**Question.** For each model under test, on new screens planned for real permissive open-source web apps whose repositories hold product evidence the plan doesn't mention: does a review by plan-design-review, or by autoplan's default lean run, name more of the design decisions that evidence supports (states and edges the screen must handle, what users need first and how they reach the next step, the viewports where the layout must work, the accessibility needs, and the app's existing components and tokens the screen should reuse) than the same model with no gstack, and than the same model with a one-line product-designer prompt?

**The public lesson this eval is after (R79), for someone building agents:** whether a written design-review procedure makes a frontier model's plan carry the design decisions its product's own evidence calls for, beyond what the same model writes when simply asked to improve the plan or told to act as a product designer; whether autoplan's default run, which carries only a short design checklist, keeps any of that; and so whether builders should ship a design-review procedure, a one-line role, or nothing.

**Claimed value, in one sentence** (the inventory's, at gstack b6155921): before code is written, the skill makes a UI plan say exactly what users will see and do (hierarchy, every state, the journey, responsive and accessible behavior, and a specific non-generic look checked against DESIGN.md and an approved mockup), with the user deciding each change, so the shipped UI is intentional instead of left to the implementer.

**Intentions scored and untested.** The inventory is wiki/research/2026-11-09-geva-412-plan-mode-intentions/inventory-plan-design-review.md. It read plan-design-review at gstack commit b6155921a564ba9ec2470fd2cb3894c05e2c2d13 (VERSION 1.98.0.0) and landed in this repository at commit 47d7964b517cb1a56c82171b89991b78af35bfee. It lists eight main intentions. This eval scores six and leaves two untested:

| Main intention (inventory wording, shortened) | How this eval scores it | Status here |
|---|---|---|
| DES-1: the plan itself ends up holding the missing design decisions, written in before implementation | every arm's scored artifact is a list of changes to the plan; a credited change is a design decision the plan lacked and the product's evidence supports | scored (primary, all classes) |
| DES-2: every screen has a clear first, second and third thing, one obvious next step and wayfinding; the journey is designed across screens | key class H; stage 3's agent-user completion, steps and dead ends | scored (primary H; stage 3 descriptive) |
| DES-3: loading, empty, error, success and partial states specified as what the user sees; edge cases covered | key class S; stage 3's forced states | scored (primary S; stage 3 descriptive) |
| DES-4: a specific, intentional look, not generic AI output | stage 3's blind pairwise of rendered screenshots against a stock generic-look control | scored descriptively only; it decides nothing |
| DES-5: responsive behavior per viewport and accessibility specified in the plan | key classes R and A; stage 3's three viewports and axe-core counts | scored (primary R and A; stage 3 descriptive) |
| DES-6: design decisions fit the design system and existing UI | key class Y, which names a real component, token or pattern in the base app; stage 3's hard-coded values against tokens | scored (primary Y; stage 3 descriptive) |
| DES-7: generated mockups the user picks settle the visual direction | not scored: it needs gstack's compiled designer binary and an image API key; no arm's container holds a key and the metering proxy admits only the arm's model | untested, in every planned eval |
| DES-8: the user decides every design change | not scored: every skill arm runs unattended and takes the recommended option | untested here; wave 2's owner-control eval |

Secondary intentions DES-9 to DES-25 are not scored. While DES-7 and DES-8 stay untested, any null on this eval reads R48 FIX-METHOD on task fit, never CUT-CANDIDATE.

**Construct fit.** The claim's core is that the shipped UI is intentional rather than left to the implementer. Each key item is a decision the screen needs, which the plan leaves to the implementer and which the product's own records support: what its data and users look like (support, research, analytics, API notes, a customer's requirement) and what the app already has (its components and tokens). A credited plan change is that decision written into the plan before code. Each skill part that carries the claim, at b6155921, and the key items it can reach:

| Skill part (plan-design-review at b6155921) | What it should add to the plan | Key items it can reach |
|---|---|---|
| Pass 1, information architecture (what the user sees first, second, third; a structure and navigation diagram) | the screen's order of attention and its primary action | H |
| Pass 2, interaction state coverage (the FEATURE by LOADING, EMPTY, ERROR, SUCCESS, PARTIAL table, what the user sees in each; empty states as features) | the states and edges the screen would otherwise ship without | S |
| Pass 3, user journey and emotional arc (the storyboard) | the steps where users get stuck or lost | H |
| Pass 4, AI slop risk (hard rules, litmus checks, readable type, contrast, focus rings) | a specific look; part of contrast and focus | A (contrast, focus), DES-4 in stage 3 |
| Pass 5, design system alignment (DESIGN.md tokens, existing components, new components checked against the vocabulary); Step 0C, existing design leverage | reuse instead of one-off styles | Y |
| Pass 6, responsive and accessibility (per-viewport layouts, keyboard paths, landmarks, 44px targets, contrast) | the viewport and assistive-technology behavior | R, A |
| Pass 7, unresolved design decisions; "proof beside each claim" (RS:94) | the gaps that would haunt the implementer, grounded in what the team knows | any class |
| Mockups (Step 0.5), the user deciding each change | the approved look; consent | none: DES-7 and DES-8 are untested |

What the score does not cover, said plainly: what really happens after a real launch (the units are constructed, so the key is what the evidence supports, not what users later hit); the look itself (DES-4 is descriptive only); mockups (DES-7); the live back-and-forth with a person (DES-8); web research (every arm runs without web tools); and whether a team would accept the changes. The skill doesn't tell the model to open a project's research or support notes; it tells it to cover every state, viewport and user step and to check the app's existing components. So a credited item needs a reviewer that either reads the evidence or reaches the same specific decision from the code and the plan, and items any plain model names from the plan alone are dropped before any arm runs (section 2).

**Models under test (R54).** anthropic/claude-opus-5-5 first; openai/gpt-6.1-sol and particle-ai/particle-1 through OpenRouter, as in the product-value and eng-review evals. All run in Claude Code with the claude-code-preset system prompt, and every model runs all four arms. Haiku and Sonnet are not models under test. Error control is per model (Holm over the two gstack contrasts), and the Opus contrasts are the preregistered headline.

### 2. Ground truth: the design decisions the product's own evidence supports

Every unit is an invented new or reworked screen for a real web app. The opening is the moment the team has written its plan and not yet built. The evidence files hold what the team already knows and the plan doesn't use. The key records the design decisions that evidence supports, as observed facts about the app and its users.

**Key items.** The author writes exactly five, one in each class. Each item has a statement of at most 30 words, written as an observed fact naming the screen, component or flow, the file where it would be handled, and the condition; a detail of at most 12 words (the specific value, threshold, component or rule the evidence fixes, used only at the 10x tier); its class; and evidence pointers (file and line).

- **S, states.** A loading, empty, error, success or partial state, or an edge (long text, zero or many records, a first-time user, a slow or failing source) the screen must handle, as the evidence shows it.
- **H, hierarchy and navigation.** What users need first on the screen, how they find or reach the next step, or a label the evidence shows would mislead.
- **R, responsive.** A viewport, device, orientation, zoom level or safe area where the evidence shows the screen is used and the layout must work.
- **A, accessibility.** A screen-reader, keyboard, focus, contrast or motion need the evidence shows among the screen's users or in a customer's requirement.
- **Y, design-system fit.** An existing component, token or pattern in this app that the screen should use instead of a new one, cited by its real file in the base app.

Examples written for this post, from no unit: "The new invoices table opens with up to 2,000 rows from one request that takes 4 to 9 seconds, so the page sits blank (src/pages/Invoices.tsx)", detail "skeleton rows, first 50 shown"; "Field technicians open the job checklist on phones in landscape at 640 by 360 pixels, where the two-column form runs off screen (app/views/Checklist.vue)", detail "640 by 360 landscape". Never advice, so the key doesn't read like any arm's style.

**Unanimous (full information).** Opus 5.5, GPT-6.1 Sol and GPT-6 Astra each get the full-information prompt (section 3) and write one plan-changes block. Each block is labelled against the key under section 6's labels by a judge outside its family (Astra labels Opus's block; Opus labels Sol's and Astra's). An item stays only when all three blocks are credited with it. At the 10x tier an item's detail is keyed only when all three credited changes also carry it (section 6's detail label); an item whose detail isn't unanimous stays in the 10x key without a detail (section 7).

**Not given away.** The same three models each get only plan.md, context/project.md and the template. An item any of the three blocks is credited with drops: a reader of the plan could name it without the evidence.

**Mentioned items.** An item whose screen and condition plan.md or context/project.md already names as something to handle is flagged mentioned by the author or by either auditor, leaves the primary and prints as its own stratum.

**Generic screen.** After the audit, Astra and Opus each label every key item against stock rows 1 and 2 (section 7) as if they were reviews. An item either marks anticipated becomes generic: it leaves the primary and prints as its own stratum. The screen reads no arm output. Stock row 3 never screens.

A unit keeps its place only with at least 3 primary items left after the audit, both drop rules, the mentioned flag and the generic screen. Drops print per step and per class.

**Wrong-way facts and the decoy.** Each unit's evidence also holds two wrong-way facts that point toward a plausible design change the rest of the evidence doesn't support, recorded in key.json. At the 2x tier the evidence adds one decoy: a concern one file raises several times about the new screen, which other files show doesn't matter for this plan. A change that matches a wrong-way fact or the decoy earns nothing and prints as a secondary (section 7).

### 3. Units

**Base apps: the frame (frozen).** One dated run of GitHub's repository search through the GraphQL API, at concurrency 1 in 1-point queries: 10 topics (admin-dashboard, admin-panel, dashboard, crm, helpdesk, inventory-management, project-management, booking-system, invoicing, self-hosted) times 5 licences (mit, apache-2.0, bsd-3-clause, bsd-2-clause, isc), each query sorted by stars and read for its first 100 results, 50 queries in all. A repository enters the frame when it is public, not a fork, not archived, not a template, has at least 200 stars, was pushed on or after 2026-06-01, has one of those five licences by GitHub's SPDX field, and has TypeScript, JavaScript, Vue or Svelte as its primary language. Repositories whose topics or README title call them a template, starter, boilerplate, UI kit or component library are left out, and so is every repository after an owner's first in frame order. The frame is ordered by sha256(seed + newline + owner/repo) with seed 20261114. Nothing else is read from GitHub: no issue, pull request or history.

**Base apps: the screen.** Down the frame order, each candidate is cloned at its default branch head (depth 1, hooks off, no filters, no LFS smudge, no repository code run on the clone) and passes a keyless file check: a web front end (react, vue, svelte or @angular/core in a package.json); at least 10 component files in one folder; a design-system source (a theme or token file, a Tailwind theme extension, a CSS file with at least 20 custom properties, or a DESIGN.md); and at least 3 routes or pages. Each candidate that passes then gets one recipe session (Opus 5.5 in the stage 3 sandbox, section 11): install from the package mirror, seed data, start command and base URL. The app qualifies when, from that recipe and offline except for the mirror, it installs, builds, serves at least 3 routes, and renders them at 375 by 812, 768 by 1024 and 1440 by 900 pixels with no uncaught page error. At most 30 candidates get a recipe session. The first 20 that qualify are the base apps, in frame order; with fewer than 16, authoring doesn't start (E_DC_SUPPLY_SHORT) and the question goes to the Captain. Each base app is pinned to the commit it was screened at, and its recipe is kept for stage 3.

**Unit files.** Each unit has three inputs and a sealed key:

- repo/: the base app at its pin, exported as a fresh git repository with one commit and no remote, stripped by section 4's export rule before anything is added, with the unit's evidence files written into it at their paths. The export happens once per unit, so no unit sees another unit's evidence;
- plan.md: the team's plan for the new screen;
- context/project.md: the project as it stands, written by the context writer below;
- key.json (sealed, never mounted): the items of section 2 with class, statement, detail, evidence pointers and every flag, the wrong-way facts, the 2x tier's decoy and evidence pointers, the validators' labels and the auditors' verdicts; and unit.json (never mounted): base app, draw position, change kind, author family and tier.

**Draw positions (frozen).** Each draw position gets a base app (round robin over the base apps in frame order), a change kind and an author family. Change kinds, cycled in an order shuffled with seed 20261114: (k1) a new list or table screen; (k2) a new form or settings flow; (k3) a reworked dashboard or overview; (k4) a new detail or record view; (k5) a multi-step flow such as an import, onboarding or checkout; (k6) a notification, inbox or activity feed. GPT-6.1 Sol authors at odd positions and Gemini 4 Argon at even ones.

**Authoring, with every prompt frozen here before any unit exists.** Every call runs through the ledger. No Claude model writes any part of a unit, its context or its key.

1. *Author (GPT-6.1 Sol or Gemini 4 Argon by position, high effort).* Neither sees the skill, its text, the arms or this post. Its input is the base app's README, its file tree, its design-system files and the source of up to 6 screen files nearest the change kind (chosen by a keyless rule: the route files whose names share the most words with the change kind's noun, then by size), then this prompt:

> You are writing a test case for reviewers of product plans. Above are a real open-source web app's README, file tree, design files and some of its screens. Change kind: <kind>. Invent one new or reworked screen of that kind that this app's team might build next, and write three things. (1) plan.md: the team's plan for the screen before building, 350 to 700 words, in the future tense: goal, users, the route and the existing endpoint or data module the screen will read, screens and flows, scope, out of scope and open questions. State at least two design decisions of your own. (2) Evidence: 5 to 8 files the team already keeps in the repository, each as a path and its text, at paths under the app's docs folder (create docs/ if it has none) that don't exist yet, each a support summary, user research notes, an analytics summary, API or backend notes, a customer requirement, earlier release notes or design notes, 1,200 to 2,000 words in all, dated before the plan. Write them as plain records of what the team knows: observations, paraphrased quotes without names, numbers and facts. No file may recommend a design or say what the new screen should do. (3) key.json: five items, one in each class. S: a loading, empty, error, success or partial state, or an edge such as long text or many records, that the screen must handle. H: what users need first, how they find or reach the next step, or a label that would mislead. R: a viewport, device, orientation or zoom level where the layout must work. A: a screen-reader, keyboard, focus, contrast or motion need. Y: an existing component, token or pattern in this app that the screen should use instead of a new one; cite its real file. Each item: {"class", "statement": an observed fact of at most 30 words naming the screen, component or flow, the file where it would be handled, and the condition, "detail": the specific value, threshold, component or rule the evidence fixes, at most 12 words, "evidence": [{"file", "line"}]}. Each item must follow from the evidence files (for Y, from the app's real code), and a reader of plan.md alone must not be able to name it: choose conditions the evidence shows and the plan doesn't hint at. Also give "mentioned", the items plan.md already names as something to handle (normally none), and "wrong_way", two facts in the evidence that point toward a plausible design change the rest of the evidence doesn't support. Invent the people, customers and numbers. Name no real person, and don't base anything on this project's real issues or history. Output one JSON object {"plan": ..., "evidence": [{"path", "text"}], "key": ...} and nothing else.

2. *Context writer (the other author family, medium effort)* sees the README, the design-system files, the file tree with each docs file's first heading (the evidence files included), and plan.md, never an evidence file's body or the key:

> Below are a project's README, design files and file tree with each docs file's first heading, and the plan for a change. Write a short description of the project for a reviewer of the plan: what the project does and who uses it, the screens and flows the plan touches as they stand now, and where the project keeps its design system and its product docs, with file paths. At most 400 words. Use only what the material says. Don't judge the plan or suggest anything.

3. *Structure and vocabulary screen (keyless).* Word counts as the prompt sets them; five items, one per class; every evidence pointer resolves to an existing file and line; every Y item cites a file that exists in the base app; every evidence path is new, sits under the docs folder and isn't an instruction file name (section 4's strip list); no date in an evidence file falls after the plan's date; no person's name from a frozen list of common first names next to a surname-shaped word, and no email address or handle. Vocabulary: no sequence of 5 words from plan-design-review's SKILL.md, sections/review-sections.md or sections/checklist.md at the pin, or from the lens line, appears in plan.md, context/project.md, any evidence file or key.json (whole words, any case, punctuation stripped), nor the skill's pass names (Information Architecture, Interaction State Coverage, User Journey, Emotional Arc, AI Slop, Design System Alignment, Responsive & Accessibility, Unresolved Design Decisions), nor the words gstack, plan-design-review, autoplan or office hours.
4. *Blind audit, by Opus 5.5 in a fresh session and by the other author family (Argon for a unit Sol wrote, Sol for one Argon wrote), high effort.* Each auditor sees exactly what the author and the context writer saw, plus everything they wrote: the author's input bundle, plan.md, context/project.md, every evidence file with line numbers and key.json. ### 7. Scoring and volume controls

**Primary, per review: A = credited primary items divided by the unit's primary items at the read tier.** Credit takes a maximum one-to-one matching between the eight changes and the key items over every change index the judge named, so one change earns at most one item. A unit-pass's A is that share; units weigh equally. The base and 2x tiers read A on their own keys.

**The 10x tier's graded primary, G.** Per primary item of the 2x key: 1 when a credited change also carries the item's keyed detail; 0.5 when a change is credited with the item and the detail isn't there; 0 otherwise. An item without a unanimous detail (section 2) scores 1 when credited and 0 when not, and the count of such items prints. G is the mean over the unit's items; units weigh equally. The strict measure D is the share of detail-keyed items credited with their detail, over units with at least one detail-keyed item. G always lies between half of A and A on detail-keyed items, so it keeps room as long as A does; a G point is not an A point, and results never compare them.

**Secondaries, all from the same labels or mechanical reads:** A by class (S, H, R, A, Y); the screen-hit share; per-change precision and the specificity score (A minus shuffled A), per arm and as the difference in differences against none; A on mentioned and generic items; the decoy-hit and wrong-way-hit rates (the share of lists with a change matching the decoy or a wrong-way fact); a mechanical evidence read (the share of sessions that opened at least one evidence file, read from the transcript, per arm); a mechanical file read (the share of items whose files the changes name by path or component name); the length-adjusted difference; and pairwise plan quality, raw and length-controlled.

**Volume can't win.** Eight changes of 40 words, normalized before judging; one-to-one credit; the specific-match rule; the generic screen; the not-given-away rule; the shuffled-key control; and the three stock rows of 2026-11-09-geva-420 section 7, word for word, judged in every packet as if they were reviews: row 1, generic UI advice; row 2, generic process advice; row 3, the skill's own checklist, which never screens. **Length.** Beside each primary, a length-adjusted difference: the unit difference in the primary regressed on the difference in the two arms' list word counts, each a mean over scored passes, with the intercept and its cluster-bootstrap interval. It is a sensitivity read, never the verdict.
