## ELI5

gstack has a skill, plan-devex-review, that reviews a plan for a developer-facing feature the way a developer-experience lead would, before anyone writes code. Its job is to make the feature easy to adopt: name the developer who will use it, set a target for how fast they reach a first working result, walk the path from installing it to upgrading it, and make every error tell a person or an agent how to recover. Nobody has measured whether it does that. The only test that touched it asked whether a review spotted flaws we had planted in a plan, plain Opus found all of them, no gstack arm ran, and the skill was marked for a cut on that record. This test grades the skill on what really happened. We take real developer-facing changes (a new command, SDK method, API endpoint, config option or breaking change) that open-source projects merged after the models' training cutoff, each with the plan its team wrote before merging. For each change we already know what happened in the 60 days after it shipped: the developers who couldn't install it or get it working, the errors they couldn't act on, the docs that were missing or wrong, the upgrades that broke, and the docs, error-message and migration fixes the team made afterwards. Each reviewer gets the team's plan and the code as it stood before the change, and writes at most eight short changes it would make to the plan. A change scores when it names the exact command or setting and the exact trouble a real developer later hit. A long list can't win, because only eight short changes count and generic advice must score near zero. We compare four setups on Opus 5.5, GPT-6.1 Sol and particle-1: no gstack, a one-line developer-experience prompt, the skill, and autoplan's default run. Judges come from a different model family than the model judged, and they are checked against known answers before any number counts. On a smaller set, a plain agent then builds each change from each reviewed plan, and a fresh agent tries to get the new feature working from the shipped docs alone.

## Before → after

Before: plan-devex-review has no main intention scored. Its only data is panel v3's developer-experience stratum (2026-11-03-geva-250-panel-v3-headroom-results), where plain Opus 5.5 found the planted flaw in 20 of 20 readings and no gstack arm ran; that produced a CUT-CANDIDATE "as seeded-flaw panels measure it", which the program's gate has since withdrawn (section 2). The outcome-per-skill plan's family X would have graded a built feature's docs-only first success, and nothing after launch.

It reports, per model with paired intervals, whether plan-devex-review, and separately autoplan's default lean run, anticipate more of the getting-started, error, docs and upgrade trouble that real developers hit than the same model with no gstack, and than a one-line developer-experience prompt. A headroom check runs first, a judge check gates every verdict, a smoke checks that each gstack arm runs its procedure, and a docs-only first success on a build subset reads what ships.

## Why it matters

The project exists to say whether gstack's skills help. The crew's plan-mode rule says a planning skill is evaluated from what it is meant to do, read in full, and that no skill is cut while one of its main intentions is untested. plan-devex-review's text loads in most full autoplan runs, because autoplan turns its developer-experience phase on for almost any plan, so a wrong answer either keeps a costly text that does nothing or cuts one that helps builders ship tools other developers can actually adopt.

## Big decisions

1. **Primary construct and score.** Options: (a) aftermath anticipation, the share of a change's real after-release developer trouble (getting started, errors, docs, upgrade) that the review's capped list of plan changes names, surface and trouble both; (b) the docs-only first success of a feature built from each reviewed plan; (c) a judged quality score of the review's developer-experience content. Pick (a) as the primary and (b) as a descriptive stage 3 on 16 units, as the program planned. Why: (a) is grounded in what developers did after the plan, dated after it, so no reviewer can copy it and no judge's taste sets it; (b) answers the "first success" part of the claim directly but costs several times a review per cell and covers only part of the claim; (c) rewards the skill's own vocabulary. What would flip it: stage 1 reading FLOOR, which makes (b) the next attempt's primary.
2. **The scored artifact.** Pick the program's shared block: at most 8 plan changes of at most 40 words, the same neutral template for every arm. Why: the template must not teach the none arm the skill's lens; the lens arm measures what one line of framing adds. What would flip it: the stock rows scoring above their limit in stage 1.
3. **One pin for both gstack arms.** gstack b6155921a564ba9ec2470fd2cb3894c05e2c2d13 (VERSION 1.98.0.0), the commit the inventory quotes, for plan-devex-review and for autoplan.
4. **autoplan in the same session (E1, O1).** The autoplan arm is Capy's default lean run (`--kind feature`): one native reviewer on the cell's own model, with the CEO and Eng lenses and the DX checklist when the plan's scope detects developer experience, one gate revision, inside the same Claude Code session, its gate answered with the recommended reply by the harness. Why: that is the form people run, and every arm must share one harness. What would flip it: the smoke showing the lean run can't run on a model, which drops that model's autoplan cells by name.
5. **Forcing the procedure.** Every gstack arm is told to run its whole procedure, taking the recommended option at every decision: plan-devex-review unattended, and autoplan interactive with its gate answered by the harness's rec persona. Exposure detectors are frozen per arm now (section 5), and the arm smoke repairs a failing arm once or drops it (D1).
6. **Leak guards with a code snapshot (B1 with H1).** Every arm sees the same offline snapshot of the repository at the change's base with no later history, so names can't be hidden by leaving the code out. Pick a per-unit alias map applied to plan.md, the snapshot and the key alike, web tools denied, per-model cutoff marking and a recognition probe that moves recognized units out of that model's primary.
7. **Models and size.** Opus 5.5 at 2 passes, GPT-6.1 Sol and particle-1 at 1 pass, every arm on every model. Pick 64 keyed comparison units and 16 keyed calibration units, found in seeded draw order through a free screen, a cheap triage read and a full key read (section 4). Why: a key is the scarce input. The free count found an unmentioned aftermath item in about 1 drawn change in 12, and in 2 of 16 fully read screen-positives (0 of 8 read negatives), so this design pays a full read only for flagged changes, and at 1 or 2 items a unit 64 units give an Opus MDD of 9 to 13 points at Holm's first step (section 13). What would flip it: the supply reading after calibration (section 4) showing that 64 keyed units cost more than the line holds, which sizes the set down to 56 or 48, or stops for the Captain under the program's own flip condition.
8. **Verdicts and the cut margin.** Separate verdicts for the skill (skill minus none) and for autoplan (autoplan minus none), Holm over those two per model; the lens is a named side comparison. A CUT-CANDIDATE needs the 95% upper bound below a frozen +0.05, every gate passing, and DX-7 scored somewhere (wave 2's owner-control eval); until then a qualifying null reads FIX-METHOD on task fit. Verdict precedence is fixed in section 11.
9. **The shared frame.** This eval and the design eval draw units from one public frame through one miner, with an exclusive developer-facing versus UI rule, so no change serves both (section 4).

## Implementation plan

### 1. The question, the claimed value and construct fit

**Question.** For each model under test, on real developer-facing changes merged after Opus 5.5's stated training cutoff: does a review by plan-devex-review, run as a user runs it unattended, anticipate more of the getting-started, error, docs and upgrade trouble that real developers hit in the 60 days after the change shipped than the same model with no gstack, and than the same model given one line of developer-experience framing? Separately: does autoplan's default lean run on the same plan?

**The public lesson this eval is after (R79), for someone building agents:** whether a written developer-experience review procedure makes a frontier model's plan changes land where real developers later got stuck (installing, reading the docs, hitting an error, upgrading), beyond what the same model writes when simply asked to improve the plan or given one line of framing; whether a planning pipeline's default run, which carries a short DX checklist among its lenses, delivers any of that; and so whether builders should ship such a procedure, a single line, or nothing.

**Claimed value, in one sentence** (the inventory's, at b6155921): the skill exists to make a plan's developer-facing product easy to adopt, by pinning down who the developer is, how fast they reach a first useful result against a benchmarked target, where the journey from install to upgrade breaks, and whether errors let an agent or a human recover, then turning each gap into an explicit, user-approved change to the plan.

**Construct fit.** The primary key's four classes (section 3) are the after-release form of the claim's outcome half: G (a first useful result: install, setup, first working use), E (errors that let an agent or a human recover), D (the docs a developer meets on the journey) and U (the upgrade end of the journey). The claim's last clause, explicit user-approved changes, is DX-7, which no unattended run can see; it goes to wave 2's owner-control eval.

**Intentions scored and untested.** Quoting the inventory (inventory-plan-devex-review.md in 2026-11-09-geva-412-plan-mode-intentions, gstack b6155921a564ba9ec2470fd2cb3894c05e2c2d13):

### 3. Ground truth: what developers met after each change shipped

Every unit is a real developer-facing change its maintainers merged and released. Its key lists what happened in the 60 days after its release, tied to the unit's own surface (the command, flag, endpoint, method, config key, install path or behavior change it added or changed), in four classes:

- **G, getting started.** An outside developer could not install, set up or reach a first working use of the surface (a missing prerequisite, an install path that failed on a platform, a first command that didn't work as documented, a setup step nobody wrote down); or a merged follow-up change fixed the quickstart, install or setup steps for it.
- **E, errors.** An outside developer hit an error from the surface that they could not act on: a message with no cause or fix, a failure reported as success, a wrong exit code, a hang without a terminal, a leaked secret in output; or a merged follow-up change rewrote that surface's error messages or error output.
- **D, docs.** An outside developer found the surface missing from the docs, documented wrongly, or unclear ("how do I", "the docs say X but"); or a merged follow-up change added or corrected its docs, examples or help text.
- **U, upgrade.** Developers upgrading to the release were broken by the change (a removed or renamed surface, a changed default, changed output), or a merged follow-up change added a migration note, a deprecation path or a compatibility shim for it.

**Who counts.** An outside developer is an issue or discussion author whose GitHub author association is NONE, CONTRIBUTOR, FIRST_TIMER or FIRST_TIME_CONTRIBUTOR. A follow-up change counts whoever wrote it. A maintainer's issue alone is not an item. **Release** is the first non-draft GitHub release, or failing that the first tag, whose commit contains the unit's merge (by git ancestry); the window is the 60 days after that release's publication. Whether that release was marked a prerelease is recorded per unit, and the post prints how many windows a prerelease opened and A on those units apart, as a descriptive check.

**Excluded:** a logic defect with no adoption angle, a request for new capability, performance tuning, anything about another part of the project, anything only an insider could know, and anything dated outside the window.

**Statements.** Each item is a statement of at most 30 words, written as an observed fact that names the surface, the developer's context where the record gives one, and the trouble: "Developers installing with the standalone binary on Windows could not run the new sync command; a DLL was missing"; "The project later rewrote the config loader's error to name the bad key and its line"; "Users upgrading found the --output flag renamed with no deprecation warning". Never advice, so the key doesn't read like any arm's style. Statements use the unit's alias map (section 4).

**Primary key.** G, E, D and U together, at most 6 items a unit: items from outside developers first, ranked by their count of distinct outside developers, then follow-up changes linked to an outside issue, then other follow-up changes, then a seeded tie-break (seed 20261109). Units weigh equally whatever their item count.

**Mentioned items.** A key item whose surface and trouble plan.md already names, as a risk, a deferral or a task, is flagged mentioned. Mentioned items leave the primary and print as their own stratum, so echoing the plan earns nothing.

**Generic screen.** After the audit, Astra and Opus each label every key item against stock rows 1 and 2 (section 8) as if they were reviews. An item either marks anticipated becomes generic: it leaves the primary and prints as its own stratum. This screen reads no arm output. Stock row 3 never screens.

**Foreseeable rating.** Each auditor rates each primary item yes, maybe or no: could a careful reviewer with plan.md and the base code have named this surface and trouble? The yes-and-maybe stratum prints beside the primary.

**Context tag.** For each item the key writer records the developer context the record gives (platform, install channel, workflow such as CI or an agent caller, experience such as a first-time user), or none. The who-hit secondary (section 8) reads it.

A unit keeps its place only with at least 1 primary item left after the mentioned flag and the generic screen. Drops are counted and reported.

### 4. Units

**Frame (shared with the design eval).** One public frame and one miner serve this eval and the design eval, as the shared frame sets them: public GitHub repositories with at least 500 stars, not forks or archived, pushed since 2026-10-01, found by a topic-search union recorded with its date, under a permissive licence (MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, MPL-2.0, ISC, 0BSD, Unlicense, CC0-1.0) or a copyleft one (GPL-2.0, GPL-3.0, LGPL-2.1, LGPL-3.0, AGPL-3.0), read from both GitHub's licence field and LICENSE at base, which must agree. A unit is one merged pull request into the default branch that:

- was created on or after 2026-07-01 and merged from 2026-07-01 to 2026-09-30, with its earliest exposure (the pull request's opening, its closing issues' opening, its earliest commit) also on or after 2026-07-01, after Opus 5.5's and GPT-6.1 Sol's stated cutoffs (section 11), so no unit is leak-exposed by the stated cutoffs, and the strict stratum (section 11) checks the unverified case that Opus's data runs to September (the free count found about 3% of developer-facing units with a closing issue opened earlier);
- is a feature or behavior change, not a fix, revert, docs, chore, dependency, release, CI-only, refactor, test-only or translation change;
- touches at least 2 non-test source files or adds at least 40 non-test source lines;
- has a plan text: its description and closing issues hold at least 120 words in their earliest recoverable versions dated before the merge;
- shipped in a release by 2026-09-30 (the first non-draft GitHub release, else the first tag, whose commit contains the merge by git ancestry), so every window closes by 2026-11-29;
- is developer-facing by the frozen classifier: Opus 5.5 and GPT-6.1 Sol label it independently from its title, description, closing issues and changed-file list (nothing dated after the merge), and Gemini 4 Argon settles a split; it gets a primary class of CLI, API, SDK or CONFIG, with BREAKING as a tag. A unit labelled both developer-facing and UI goes to the side the shared frame's line-share rule names, so no unit serves both evals;
- has a base checkout of at most 150 MB without .git, and no .claude/ folder or .mcp.json at any depth at base;
- is one of at most 3 units from its repository, and no unit's window holds another unit.

The 38 units the free count read are excluded (their digests sit in the shared frame's records). Draws are seeded: seed 20261109, order sha256 of the seed, a newline and owner/repo#number.

**Supply count (free, 2026-11-09).** A count with no model calls put the frame at about 5,500 developer-facing units capped at 3 a repository (90% interval 3,756 to 7,243), about 4,300 of them released by 2026-09-30, and found keys scarce. In 12 full 60-day reads of a blind draw, 1 unit had items its plan didn't name (4 of them, mostly from outside issues). A free screen then ran on a fresh pool of 54 units: 16 (30%) were screen-positive, and full reads of all 16 and of 8 negatives found unmentioned items in 2 positives and in no negative, 3 items in all, every one from a follow-up change. So the 12-unit read puts about 1 drawn change in 12 with a key item its plan didn't name, and the screen pilot 2 keyed among 16 read positives and 0 among 8 read negatives, with the other 30 negatives unread (so 2 in 54 is only a floor for the pool), all before the audit, the cap and the generic screen, and from small samples with wide intervals. The funnel below exists to find those changes without paying a full read for every draw.

**The key funnel.** Units are taken in draw order, each only after its window closes, through three steps.

1. *Free screen, no model.* The miner lists candidates in the unit's window from three sources: outside issues and discussions, and merged pull requests that touch docs, help or error paths, that name one of the change's own identifiers (the pilot's rules, frozen verbatim in the build's fixture: at most 6 identifiers, with generic tokens and any token found in more than 10% of the window's items dropped); any issue, discussion or pull request in the window that cross-references the unit's pull request or its closing issues; and any merged pull request in the window that changes a file the unit changed and also a docs, help or error path. A unit with no candidate drops as screen-negative.
2. *Triage, Gemini 4 Argon at medium effort.* Argon, from a family that none of the models under test belongs to, reads the unit's source plan text, its identifiers, and each candidate's title, author association and body passage around the match. It flags the unit when any candidate could be a G, E, D or U item about the unit's surface under section 3, and it flags when in doubt. An unflagged unit drops as triage-negative.
3. *Key read, Opus 5.5 at high effort.* The key writer reads the flagged unit's whole window: the title of every issue, discussion and pull request created in it, the body of every one that touches the unit's surface, and every candidate in full. It writes section 3's key, with evidence pointers and dates for each item.

A unit enters a set only with at least 1 primary item left after the audit, the mentioned flag and the generic screen. Every count at every step is reported. Planning figures: 30% of draws screen-positive and 12% of positives keyed (the pilot), and a triage that flags about a third of positives and keeps 9 in 10 of their keys (an assumption the miss sample checks). That is about 31 draws, 9 triage reads and 3 key reads for each keyed unit. The funnel keeps about 1 draw in 31, fewer than the roughly 1 in 12 that hold an item, because it drops screen-negative and triage-negative changes, some of which hold items; the miss sample measures that loss. The calibration set draws from the units released by 2026-09-09, an early-release subset. In all, about 2,700 draws for the 86 keyed units: inside the roughly 4,300 units released by 2026-09-30, but near the low end of that estimate's interval, which is why supply rule 3 exists. The miner paces GitHub's API so the shared quota stays above its floor (section 16).

**Miss sample (descriptive).** 24 dropped units from the calibration draws, 12 screen-negative and 12 triage-negative in seeded order, get a key read anyway. Their item rates print as the funnel's miss rates, so the post can say how much real trouble the funnel leaves out. They never enter a set.

**What population this defines.** Results speak for developer-facing changes in popular open-source projects whose first 60 days after release left public, findable adoption trouble that the plan didn't name. Most changes leave none, and this eval can't score a review's worth on those; the post says so beside every verdict. Because the funnel favors busy repositories, every primary also prints with its interval and sign flips clustered on repository, a sensitivity that decides nothing.

**Unit files.** Each unit has two inputs and a sealed key:

- repo/: the repository at the unit's base (the merge's first parent), aliased, with the repository's own instruction files stripped (below), as a fresh git repository with one commit and no remote, so tools that call git work and no later history exists in the container (H1);
- plan.md: the team's plan, from the frozen rewrite below, aliased;
- key.json (sealed, never mounted): section 3's items with class, statement, evidence pointers, dates, context tags and flags, the auditors' ratings, and the unit's alias map.

**Repository instructions stripped.** Claude Code loads a project's CLAUDE.md and CLAUDE.local.md by itself, from the working directory and from any folder whose files it reads, along with every file they @import. A unit repository's own instructions could then impose a review procedure on an arm, or react to whether a skill is installed, and change scores in the arms this post calls clean. So the snapshot builder removes every CLAUDE.md, CLAUDE.local.md, AGENTS.md and .claude/AGENTS.md, at any depth, from the snapshot before any arm setup runs, the same for every arm, and records per unit which files it removed; the post prints how many units had them. With those files gone, nothing @imports anything; a file one of them imported stays as ordinary project text. AGENTS.md goes too: a session with no CLAUDE.md reads AGENTS.md as project instructions, so keeping it would reopen the same leak. Files under .claude/rules, which load at launch, can't reach an arm, because units with a .claude/ folder at any depth are out of the frame. The strip removes only the unit repository's own instructions. In the gstack arms, gstack's install runs after the strip, and whatever instructions it writes into the project or the Claude Code configuration (its skill routing included) are part of that arm, as they are for anyone who installs gstack; the strip never removes them. The dry run checks both directions (section 15).

**Plan rewrite (frozen prompt).** The authoring model (Opus 5.5) sees only the earliest recoverable pull request description and its closing issues, never the diff, review comments or anything dated after the merge:

> Below is the description of a change a software team made, and the request that led to it if there was one. Rewrite it as the plan the team would have written before building: future tense, the same goals, scope, commitments, constraints and open questions, at about the same length. Keep every decision the description states, including any docs, error messages, migration notes, tests or rollout it promises. ### 7. Judging (R78)

**Who judges which lists.** GPT-6 Astra (openai/gpt-6-astra) labels every list a Claude model wrote (Opus arms). Opus 5.5 labels every list a GPT model wrote (Sol arms). particle-1 lists go to a cross-family panel of Astra and Opus; where they split, Gemini 4 Argon (google/gemini-4-argon, through OpenRouter with data collection denied) casts a third vote, and the label is the median of the three, which for binary labels is the majority. Stock rows, oracle lists and shuffled-key packets go to the same judge as the lists beside them. Production label calls run at medium reasoning effort, the judge-check pass at maximum. Every result records the judge model, the version the provider reported and the effort, and judge calls are cached by model, version, prompt digest and packet digest.

**Labels.** Each packet holds one unit-pass: the unit's key items (aliased statements only) and that model's normalized lists for the unit from all four arms, plus the three stock rows, shuffled with a seed and labelled only by random ids. For each list and each key item the judge gives three labels and names every change index behind each yes:

- *anticipated* (primary): one change names, in substance, both the specific surface the item records (the command, flag, endpoint, method, config key, install path or upgrade step) and the specific trouble (the failing step, the missing or wrong doc, the error a developer couldn't act on, the break on upgrade), so that a team acting on it would have prevented the trouble or shipped its fix before launch. A category alone doesn't match ("improve error messages" doesn't match "the sync command printed 'invalid state' with no fix when the token had expired"); the right trouble on another surface doesn't match; a change that names the surface and the trouble in other words does. A change that names the developer context and a trouble without the surface earns no primary credit; it counts in the who-hit secondary.
- *surface hit* (secondary): one change names the item's surface, whatever the trouble.
- *who hit* (secondary): one change names the item's developer context (its context tag), whatever the trouble; items tagged none take no who label.

The brief gives three generic match and no-match examples written for this post, from no unit.

**Shuffled-key control.** Each list is also labelled against a seeded derangement of keys over all audited units: another unit's key from the same repository where one exists, otherwise from the same developer-facing class and, where possible, the same language. A list's shuffled A measures how far its changes match a nearby change's aftermath rather than this one's.

**The judge check, before any judge number counts.** It must not be circular. The check set is labelled in a separate pass, with its own audit prompt that asks for the quoted change behind each anticipated label, at maximum reasoning effort, by both Astra and Opus. Each production judge's check set is every stage 1 list (the none lists of all three models and the smoke lists; each judge also labels the other models' stage 1 lists at production effort, for the check only), plus anchors: stock rows 1 and 2 as known-bad lists (the generic screen removed what they match); one verbatim oracle list per calibration unit as known-good, written by a script that turns each primary item into a change naming its surface and trouble; one paraphrased oracle list per calibration unit, where Gemini 4 Argon rewrites each oracle change in its own words, keeping the surface and the trouble, so matching it takes reading rather than word overlap; and one near-miss list per calibration unit, where the script pairs each item's surface with another item's trouble, as known-bad cells that test the both-parts rule. Stock row 3 is labelled like any list and is never an anchor. Gold labels are the cells where Astra and Opus agree in that pass. Each production judge needs at least 40 gold cells of each class (anticipated and not), from at least 40 distinct lists counted across both classes. Verbatim oracle cells supply at most a quarter, and verbatim and paraphrased oracle cells together at most three quarters, of a judge's anticipated gold cells. At 16 calibration units of 1 or 2 items, each oracle anchor set gives about 24 anticipated cells, so the minimum is reachable once real lists add about 10 anticipated gold cells, which about 166 stage 1 lists give near an A of 0.05. Each production judge (Astra on Opus lists, Opus on Sol lists, the panel on particle-1 lists) is then scored on its gold cells from its own production labels: its catch rate on bad outputs, its false-fail rate on good ones and Cohen's kappa, on all gold cells and on real-list cells alone. A judge passes only when both kappas reach 0.6. A judge that fails, or is short of gold cells, makes only its model's contrasts read untested (judge); only the Opus lists' judge failing in stage 1 ends the eval (section 10). In stage 2, whole calibration packets (one unit-pass of a calibration unit, aliased and formatted like comparison packets, with random ids) are inserted blind into each production judge's queue at seeded positions until they hold 40 gold cells under the same oracle caps; a judge whose stage 2 kappa on them falls under 0.6 makes its model's contrasts untested (judge). Gold cells print by arm and by class.

### 8. Scoring and volume controls

**Primary, per review: A = credited primary items divided by the unit's primary items.** Credit takes a maximum one-to-one matching between the 8 changes and the key items over every change index the judge named, so one change earns at most one item. A unit-pass's A is that share; a unit's arm score is the mean over its passes; units weigh equally.

**Secondaries, all from the same labels:**

- A by class: A_G, A_E, A_D and A_U;
- the surface-hit share and the who-hit share (DX-1's after-launch reading);
- per-change precision (the share of changes credited with any item) and the specificity score (A minus shuffled A), per arm and as the difference in differences against none;
- A by key source: items from outside developers against follow-up changes;
- A by developer-facing class of the unit, each with its MDD (descriptive);
- A on mentioned and generic items, and the foreseeable stratum;
- the length-adjusted difference: the unit-pass difference in A regressed on the difference in the two lists' word counts, with the intercept and its cluster-bootstrap interval;
- per-marker exposure rates (section 5) and, for the skill, A on sessions where each marker showed against sessions where it didn't, descriptive only;
- cost per review and per credited item.

**Volume can't win.** Eight changes of 40 words, normalized before judging; one-to-one credit; the specific-match rule; the generic screen; the shuffled-key control; and three stock rows judged in every packet as if they were reviews. The stock rows, frozen:

- **Row 1, generic developer-experience advice:** (1) Add a quickstart with copy-paste install and first-run commands. (2) Make every error message say what went wrong and how to fix it. (3) Document every new option and command with an example. (4) Add deprecation warnings and a migration guide for any breaking change. (5) Give every command a --help with examples. (6) Test installation on Linux, macOS and Windows. (7) Validate configuration at startup with clear errors and sensible defaults. (8) Add a troubleshooting section to the docs.
- **Row 2, generic process advice:** (1) Write a short design doc and get it reviewed before coding. (2) Add unit and integration tests for the new code. (3) Run the tests and linters in CI on every pull request. (4) Release it behind a feature flag first. (5) Add telemetry to measure adoption and failures. (6) Ask a few users for feedback before the release. (7) Keep the change small and ship it in steps. (8) Update the changelog and release notes.
- **Row 3, the skill's own checklist (never used to screen):** (1) Name the target developer, their context and how many minutes they will tolerate. (2) Set a time-to-hello-world target under five minutes with a one-command install. (3) Specify the magical moment and make sure the plan delivers it first. (4) Make every error follow the agent-ready contract: what failed, the fix, a code, a docs link. (5) Trace the journey: discover, install, hello world, real use, debug, upgrade. (6) Add --json output and a non-interactive flag for agents and CI. (7) Ship a migration guide and a codemod with every breaking change. (8) Write copy-paste examples that run unmodified in CI.

**Stock checks.** Rows 1 and 2 should anticipate no primary item after the screen, so their count is a consistency check on the judges. The screen's two models are also the judges, so in either stage a row 1 or 2 credit means a judge contradicted its own screen label: a self-consistency check with little power, while the judge check and the shuffled key carry the guard against volume. Row 3 guards against the skill's own generic moves. A model's stage reads STOCK FAIL when row 1 or row 2 is credited with a primary item on more than 2 of the 16 calibration units (stage 1) or on more than one comparison unit in eight (stage 2). In stage 1 a stock fail on Opus lists ends the eval, and one on Sol or particle-1 lists makes that model's contrasts read untested (stock); in stage 2 a stock fail makes only that model's contrasts untested (stock). Row 3 never triggers STOCK FAIL: its credits print per model beside every skill verdict, as what the skill's own checklist earns with no review.

### 9. Attacks on the scores, answered before code

1. *Volume and verbosity.* The 8-by-40 cap, normalization, one-to-one credit, the stock rows, per-change precision and the length-adjusted read.
2. *Generic hits.* The specific-match rule (surface and trouble both), the generic screen, the shuffled-key control and the stock checks, including a row built from the skill's own checklist.
3. *Self-preference.* No model judges its own family's lists; particle-1 gets a three-family median.
4. *A judge that labels badly.* The non-circular judge check with known-bad and known-good anchors, both kappas at least 0.6, and the blind stage 2 re-check.
5. *Style revealing the arm.* The skill's words (persona, magical moment, TTHW) could tip a judge. Normalization strips formatting, labels are factual matches against a key, and a descriptive probe asks Astra to guess the arm of 30 random normalized lists; above 70% correct, the post flags it.
6. *Hindsight.* Much developer trouble is hard to foresee. The headroom band's floor catches a mostly unforeseeable key, and the foreseeable stratum prints.
7. *Echoing the plan.* Mentioned items leave the primary.
8. *Leaks.* Inputs come only from material dated before the merge, with names replaced through the alias map; the snapshot holds no later history; the window starts after Opus 5.5's stated cutoff; web tools are denied; each model's cutoff is checked, and a recognition probe moves recognized units out of that model's primary (section 11).
9. *Busy projects dominate.* Units weigh equally with at most 6 primary items each, and at most 3 units come from one repository.
10. *The format is the lift.* Every arm writes the same block; the lens arm and the stock rows test how much the framing alone carries.
11. *Effort, not procedure.* Skill sessions read more and take longer. That is the procedure's mechanism, so it counts, and cost per credited item prints beside each contrast.
12. *Failures scored as misses, or dropped in an arm's favour.* Section 6's table: failures outside the agent are missing, never 0; stops the arm causes score 0 after one retry, and a sensitivity read treats them as missing; a missing-rate gap switches the primary to intention to treat.
13. *Key items only an insider could write.* Items come from public records in the window, follow-up changes are merged commits, and auditors check every item against its records.

**Smoke rules (D1), fixed now.** Every gstack arm gets at most one repair, and an arm that fails after it is dropped.

1. *Parse.* Each gstack arm must return a parsable block in at least 5 of its 6 Opus smoke sessions.
2. *Exposure.* Each gstack arm must be exposed (section 5) in at least 5 of its 6 Opus smoke sessions, and in at least 1 of its 2 sessions on Sol and on particle-1.
3. *autoplan runs.* On each model, the lean run must reach its gate with its reviewer on the cell's model in at least 1 of 2 sessions (5 of 6 on Opus); a model where it can't is named, and its autoplan cells don't run.
4. *Cost.* An arm whose Opus smoke median exceeds half the session limit, or with 2 or more of its 6 Opus sessions stopped by a limit, fails; so does an arm whose measured medians, with every other arm at its own, put the stage 2 projection past its cap after the cut list.
5. *The one repair.* A parse or exposure failure on plan-devex-review is repaired with the harness's Stop hook: gstack-evals code that runs the arm's detector when the session tries to stop and, while the procedure hasn't shown, blocks the stop with one fixed message naming the missing outputs, at most twice; the arm is then named "with an enforced procedure" in every headline. A parse or exposure failure on autoplan is repaired with gstack's own stop gate at the same pin (the install's autoplan gate option), named "with gstack's stop gate". A cost failure from limit stops is repaired by doubling every arm's session limits on every model, all alike, and only when the re-projection at the doubled limits fits the stage 2 cap after the cut list; otherwise the arm drops (rule 6). The repaired arm reruns its smoke (6 Opus, 2 each on Sol and particle-1) and must pass every rule; a repair applies to that arm on every model.
6. *Drop.* An arm that fails after its repair reads FIX-METHOD on the instrument on the models where it failed; its stage 2 cells there don't run, and it enters Holm with p = 1.

### 11. Stage 2: the comparison, verdicts and their precedence

The comparison set is 64 units, or the size supply rule 2 or 3 picked (section 4), fixed with its digest before the first stage 2 lease. Opus 5.5: all four arms at 2 passes. Sol and particle-1: all four arms at 1 pass. Each model-pass is one frozen run, its units' cells interleaved in a seeded order, in the order section 14 fixes.

**Primaries, per model (F1):** plan-devex-review minus none, and autoplan minus none, on A; Holm across those two. The Holm family is frozen at those two: an arm that doesn't run (dropped at smoke, stopped at the interim) enters with p = 1. A unit's arm score is the mean over its passes; differences pair by unit, clustered on the unit (taken from each review's unit field, checked so the cluster count equals the unit count); each difference has a 95% cluster-bootstrap interval (10,000 draws, seed 20261109) and a two-sided cluster sign-flip p (10,000 flips, seed 20261109). Every comparison prints paired, with its interval and the count of units whose A got worse.

**Named side comparisons (decide nothing on their own):** plan-devex-review minus the lens (the trim reading); autoplan minus the lens; lens minus none; plan-devex-review minus autoplan; and every section 8 secondary per arm.

**Leak exposure (B1).** Before stage 1, the build records each model's stated training cutoff from its provider's published documentation (the product-value build's cutoffs.json as of 2026-11-08: Opus 5.5 June 2026, with the repository's earlier records noting data possibly collected to September 2026, unverified; GPT-6.1 Sol 2026-04-30; particle-1 none published). A unit whose earliest exposure (its pull request's opening, any closing issue's opening, its earliest commit date) falls before a model's stated cutoff, or that the recognition probe names correctly for that model, is leak-exposed for that model: descriptive, out of that model's primaries. If more than a quarter of a model's units are leak-exposed, its primaries read untested (leak). A model with no published cutoff runs with that limit stated beside its results. **The recognition probe:** each model, with no tools, sees plan.md and the first 40 lines of the snapshot's README (both aliased) and is asked to name the real project and say what changed in it in the 60 days after this change shipped; a correct project name, checked mechanically against the unit's real names, marks the unit recognized for that model. For Opus's possible late data, A also prints by merge month, and a strict stratum of units first exposed on or after 2026-08-01 prints beside every Opus primary.

**Interim exposure check.** On every model, after a gstack arm's first 24 stage 2 sessions (16 on Sol and on particle-1, which run one pass), an arm whose exposure is under 0.80, the line below which its contrast reads untested, pauses: it starts no more paid sessions on that model, its open lease settles at the spend so far, and the reading goes to the Captain before anything more runs in that arm on that model. Nothing is repaired or retried without the Captain's word. If the Captain stops the arm there, its cells on that model read untested and its remaining cap is released.

**Verdict precedence, fixed now.** Each gstack arm on each model gets exactly one verdict word and one R48 reading, decided in this order; the first step that applies decides.

1. *Stage 1.* Not HEADROOM: no stage 2 runs, and the eval reads per section 10 (FLOOR, CEILING, STOCK FAIL or NO READ).
2. *Untested.* Any of these makes the contrast **untested**, with its named cause, and its R48 reading FIX-METHOD on that cause: the arm dropped at the smoke on that model, or stopped at the interim; exposure under 0.80; coverage under 0.90; contamination over 5%; a stock fail on that model's stage 2 lists; that model's judge failing its check or its stage 2 re-check, or short of gold cells; leak exposure over a quarter of its units.
3. *helps* (or *hurts*): Holm p at most 0.05, the 95% interval excludes zero, and the specificity contrast, the paired difference in differences per unit (A_arm minus shuffled A_arm) minus (A_none minus shuffled A_none) with the same cluster bootstrap, has an interval that excludes zero in the same direction.
4. *not shown*: the interval excludes zero but step 3 fails (Holm or specificity). It prints with the requirement it failed.
5. *no measurable difference*: the interval includes zero. The MDD and the interval print with it.

Then the R48 reading, from the verdict word:

- **helps → KEEP** for plan-devex-review on that model, worded "its plan changes anticipate more of the trouble real developers hit after release". For autoplan the same reading is worded "autoplan's default run anticipates more ..." and is a keep for the lean run as a whole on this trouble; it can't say whether the DX checklist, the CEO and Eng lenses or the gate revision carry the gain, because the arm differs from none in all of them. Either is **flagged** when stage 3 shows that arm's builds reaching first success less often than none's with an interval that excludes zero. helps always wins over every reading below.
- **CUT-CANDIDATE** for plan-devex-review on a model needs all of: the verdict is not helps; the 95% upper bound of skill minus none is below the frozen margin of +0.05; admitted headroom; no CEILING flag on that model; exposure at least 0.80; coverage at least 0.90; passing stock and judge checks; no leak; and every main intention of the skill scored in some eval. DX-1 to DX-6 have scores here; DX-7 needs wave 2's owner-control eval. Until that eval's results post has scored DX-7, a contrast that meets every other condition reads **FIX-METHOD on task fit**, and the post prints its upper bound and says it would read CUT-CANDIDATE once DX-7 is scored. A hurts or not-shown verdict reaches CUT-CANDIDATE on the same conditions.
- **autoplan never reads CUT-CANDIDATE here.** This eval scores only its DX phase (AP-DX-1) and none of its other main intentions. A contrast that meets every CUT-CANDIDATE condition but the last reads "the lean run as a whole shows no DX gain", an R48 lead for gstack to test whether the DX lens earns its place, which only an autoplan-without-DX control could settle; autoplan reads FIX-METHOD on task fit.
- **FIX-METHOD on power**: not helps, and the upper bound at or above +0.05. The post prints the gain the interval rules out.
- **CEILING flag**: a model whose none arm reads above 0.65 on its primary units, in stage 1 or stage 2, carries the flag, and no CUT-CANDIDATE or whole-run lead can come from that model; its null reads FIX-METHOD (saturation).
- **The one-line framing carries it** is written only when skill minus none reads helps and skill minus lens has an upper bound below +0.05: an R48 lead to cut the lines of the skill that don't help. When lens minus none helps but skill minus lens doesn't meet that bound, the post writes that the framing carries part of the gain, which is no lead to cut.
- The skill's verdict and autoplan's verdict never combine into one gstack verdict.

**What each result means, written now.** A KEEP for plan-devex-review on Opus says the full procedure makes plans land where developers later struggle, and the post names which classes carry it. A KEEP for autoplan says the default lean run, as a whole, carries a benefit on this trouble that people get by default; which of its parts carries it is not tested here. A KEEP for the skill with autoplan null says the default run leaves the benefit behind, a lead for gstack to load more of the skill in the lean run. CUT-CANDIDATE (once DX-7 is scored) says plain Opus already anticipates this trouble as well as the skill. Each goes to the Captain plainly, losses included, and through it to GStack Minder.

### 12. Stage 3: docs-only first success on a build subset (I1, M1)

Stage 3 keeps family X's build score as a descriptive secondary (M1): does a plan reviewed by each arm lead to a feature a fresh developer can get working from its docs alone, with errors that say how to recover? It decides nothing except the KEEP flag above, and it runs after stage 2's Opus pass 1, whatever stage 2's verdict.

**Build units.** 16 comparison units (4 of each developer-facing class where supply allows), drawn in seeded order among units whose project builds and installs in the sandbox at base and at the merge. For each, written before stage 3 by the key writer from plan.md and the real merged change, blind to every arm: one frozen first-success goal ("use the new <surface> to <outcome>") with a checker script that decides it, and 3 frozen misuse probes (for example the new command with a required argument missing, a bad config value, a missing credential). An auditor runs the goal and the probes against the real merged tree, where the goal must pass and each probe must reach the new surface's error path; a unit that fails twice is replaced in seeded order.

**Build arms.** Four per unit, 1 trial each, all by Opus 5.5 in Claude Code with no gstack: plan.md plus each arm's normalized block from its stage 2 Opus pass 1 (none, lens, plan-devex-review, autoplan), mapped back from aliases to the real names. The prompt: "Implement the plan in plan.md in /work/repo, with its docs and tests. A reviewer's notes on the plan follow; use them as you see fit." then the block. Session limits frozen: $8, 300 turns, 2 hours.

**Docs-only first success.** A fresh Opus 5.5 agent with no gstack gets a fresh sandbox with the built artifact installed (the package, binary or server built from the arm's final tree), the tree's README, docs/ and the artifact's help output, and no source tree; the frozen goal; and 20 turns. The checker decides first success. Then the agent runs the 3 misuse probes, and each output is scored on the contract's checkable fields: it names what failed; it names a fix or next step; it exits non-zero (a CLI) or returns a problem-details body (an API); it carries no secret value; it returns within 10 seconds with stdin closed. The first two fields are judged by Astra (the builds are Opus's); the rest are mechanical.

**Measures, per build:** first success (0 or 1); turns, minutes and failed commands to first success; the share of probes meeting every field (DX-5); the share of the goal's steps the README states (mechanical, from the agent's commands against the README's code blocks). **Readout:** paired by unit against the none block, each with a 95% cluster-bootstrap interval and the worse count.

**Sandbox (I1).** Every build session and every docs-only session runs in its own throwaway Ubicloud VM, created for that run and destroyed after it: no keys inside (the metering proxy runs on the controller and holds them), network only to the metering proxy and a package mirror pinned for the run, no drive mounts, the run user's linger set, apt's timers stopped before anything runs, UBI_OWNER set to the run thread's code and a TTL that covers the session. After each run the controller records the VM's network log and a file list (stat data only) and checks that no connection went anywhere else; a breach marks that build contaminated, missing, and stops the stage for the Captain. Repository code runs only inside these VMs, never on the controller or a Capy machine.

### 13. Power and MDD (G1)

power.py (attached, seeded 20261109, no key) adapts the engineering-intentions eval's script. It simulates A over units of 1 to 2, 1 to 3 or 2 to 4 primary items, with item noise (sd 0.8 on the logit scale) around each unit and effect noise tau 0.5, and runs the paired sign-flip test at alpha 0.05 and at Holm's first step over the two verdict contrasts (alpha 0.025). From power.txt, the MDD at 80% power and Holm's first step:

The projection rerun before stage 2 re-estimates the variance components and the item mix from stage 1 and the audited units, reprints every MDD at the final size, and that figure is the MDD every verdict prints. **CUT-CANDIDATE's operating characteristics** (power.txt parts B and C). At 64 units on Opus with 1 or 2 items, a true difference of exactly +0.05 reads CUT-CANDIDATE in 2.7% of simulated runs, so the margin rule rarely cuts a skill that is truly worth 5 points (G1). A true zero reads CUT-CANDIDATE in 26% to 40% of runs and a true -0.05 in 79% to 89% (power.py simulates a negative difference as the mirror of a positive one, so those rows put the none arm at the stated control plus 0.05 and the gstack arm at the control); the rest read "no measurable difference" and FIX-METHOD on power. On Sol and particle-1 at 1 pass, a true +0.05 reads CUT-CANDIDATE in 2.9% of runs and a true zero in 17% to 21%. Making CUT-CANDIDATE the usual reading of a true zero (above 80% of runs) would take about 256 units at control 0.20 and 320 at 0.35, at 1 or 2 items (power.txt Part C: 192 units read 0.799 at 0.20), which this aftermath can't supply, so most nulls here will read "no measurable difference", no cut follows from them, and the post states which of these applies.

The prior, stated before data: a gain of 5 to 15 points on Opus is plausible, because the skill walks the getting-started path, the error messages, the docs and the upgrade path by name, which is what G, E, D and U record, while plain Opus asked for plan changes leans toward the feature's own logic; the lens may carry part of it. At a 9 to 13 point MDD this design can miss a real gain under about 10 points, and it says so in every null.
